# フェーズ019: 実運用障害調査と解決計画

## ゴール

GitHub 公開版 `0.1.0`（commit `8163de9`）を uv 経由で使用し、3作品のスペースオペラ掌編を制作した実運用テストで検出した障害を、再現条件、根本原因、影響範囲、安全性への影響に分けて調査する。調査結果から、修正の優先順位、実装単位、移行方針、回帰テスト、性能受入条件を含む解決計画を作成する。

## 調査対象

1. `init` 直後の `run` が、未追跡の `.story-pipeline/state.json` を理由に安全停止する。
2. 初回の作品作成要求で、planner が推測した `targets` と要求本文の完全一致制約が衝突し、3件すべてが要求解釈で失敗する。
3. failed run の再開時に要求本文の変更を受け入れる一方、run の `request_sha256` を更新せず `validate` が恒久的に失敗する。
4. 本文制作で、本文 JSON の機械検査と canon・人物状態更新の evidence 完全一致検証が高頻度で失敗する。
5. 本文が採用可能でも、後続の知識更新抽出失敗により本文候補を保存せず、高コストの再生成を要する。
6. 本文工程で、長時間の無出力、トークン上限切断、概要だけの終了コード9が発生し、利用者が停止工程と再開方法を判断できない。
7. 1章1話の計画と本文を完了しても `phase=episode_planning`、`next_chapter=1`、`next_episode=2` となり、章改稿へ進まず `validate` が番号矛盾を報告する。
8. 実行記録のトークン数が `null` で、再試行、待機、論理呼出し、通信試行の所要時間も十分に分離できず、性能と費用を評価しにくい。

## 保存済み調査資料

- 作業ルート: `/tmp/story-pipeline-space-opera-test/`
- 作品: `orbital_lighthouse`, `memory_fleet`, `gravity_garden`
- 各プロジェクトに要求、報告、状態、run JSON、生成物、Git 履歴を保存済みとする。
- 一時領域が消去されても調査可能なよう、必要な事実と秘密を含まない最小再現データをリポジトリ内のテストへ転記する。

## 完了条件

- 各障害に対し、安定した再現手順または再現できない条件を記録する。
- 推測ではなく、コード経路、永続データ、テスト結果に基づく根本原因を特定する。
- 利用者データ、Git 履歴、再開可能性を壊さない修正方針を定める。
- 障害間の依存関係と優先順位を明示し、独立にマージ可能な実装フェーズへ分割する。
- 各修正の API 非依存回帰テストと OpenRouter 統合テストを定義する。
- 正常系の成功率、所要時間、呼出し数、トークン数、失敗時の成果保全について測定可能な受入条件を定める。
- 調査結果と解決計画を `.task/019-002_実運用障害調査結果と解決計画.md` にまとめる。
