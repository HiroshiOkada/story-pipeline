# フェーズ019 調査結果と解決計画

## 調査基準

- 対象リリースは `pyproject.toml` が `0.1.0` を示す commit `8163de9`（`Merge initial release readiness phase`）である。保存済み3作品は、この GitHub 公開版を uv 経由で実行して作成された。

優先度P0として利用開始不能と成果喪失を先に止め、P1で診断・性能計測を完成する。採用案と実装先は次のとおりである。

## 保存済み3作品の事実

### 共通の時系列

各作品は request 0000〜0004 を順に実行し、構想、基礎設定、全体構成、話計画、本文を作成した。0000〜0003 の正常工程は26〜60秒程度、0004 の本文工程は約18〜30分を要した。初回要求は3作品すべてで一度失敗し、要求へ対象を明記して同じ run を再開した。本文工程も全作品で一度以上失敗し、設定変更または要求変更後に同じ run を再開した。

| 作品 | request 0004 所要時間 | generation / review | 記録された主な失敗 | 完了までの本文試行 |
| --- | ---: | ---: | --- | ---: |
| orbital_lighthouse | 20分07秒 | 17 / 2 | 知識更新候補の形式検証 | 2回 |
| memory_fleet | 30分07秒 | 18 / 2 | 知識更新候補、トークン上限、本文候補不成立 | 4回 |
| gravity_garden | 18分55秒 | 16 / 2 | 知識更新候補、本文候補不成立 | 3回 |

`call_counts.generation` は planner 等も含む論理呼出し数であり、`model_attempts` はそれぞれ19、20、18件であった。すべての `model_attempts[].token_count` は `null` であるため、保存記録だけから費用や入出力 token を復元できない。

### 共通の最終状態

3作品とも `episodes/0001.md` と `completed_episodes=[1]` を保存している。一方、状態は `phase=episode_planning`、`current_chapter=1`、`next_chapter=1`、`next_episode=2`、`completed_chapters=[]` である。各 Git 履歴には要求入力と run 終了のコミットが残り、失敗した run の終了コミットも保持されている。

### 失敗分類

1. 初期導線: `init` が初期 commit を作らないため、未追跡の状態ファイルによって最初の `run` が安全停止した。
2. 要求契約: 初回 request 0000 は3作品すべてで `要求本文に明示されていない対象です: targets/0` により失敗した。
3. 再開整合性: request 0000 の run JSON は変更前の `request_sha256` を保持する一方、step と `input_hashes` は変更後要求の hash を保持する。
4. 本文・知識更新: 全作品で、採用可能な本文の評価後に canon・人物状態更新候補の形式検証が失敗した。
5. 上限・診断: memory_fleet でトークン上限切断が記録された。長い無出力時間と終了コード9は run JSON だけでは原因を復元できない。
6. 状態遷移: 1章1話を完了しても次の話計画を指し、章改稿へ遷移しない。
7. 観測性: 呼出し集計はあるが token はなく、論理呼出し・transport 再試行・待機の時間を分離できない。

## 根本原因と解決計画

### I-01: `init` 直後に `run` できない

#### 再現とコード経路

一時ディレクトリに `story-pipeline init` を実行し、そのまま API 非依存の `inspect_run_preconditions` を呼ぶと、`init` は終了コード0で `Run: story-pipeline run` と案内するが、事前検査は終了コード5相当の `未追跡の CLI 管理ファイルがあります`、location `.story-pipeline/state.json` で停止する。

- `create_scaffold` は設定、要求0000、状態、`.gitignore` を作る。
- `_init_project` は必要なら `git init` するが、初期 commit は作らない。
- `classify_path` は `.story-pipeline/state.json` を `managed` に分類する。
- `inspect_run_preconditions` は未追跡の `managed` を無条件で拒否する。この検査はモデル接続と開始時 commit より前にある。
- `_changed_start_paths` と `commit_start_inputs` は要求と設定だけを開始時 commit の候補にし、初期状態と `.gitignore` を初回だけ収容する契約を持たない。

したがって原因は Git 分類の誤りではなく、「init は未コミット scaffold を正常結果として返す」「run は全管理ファイルが追跡済みであることを前提にする」「表示は直後の run を案内する」という3契約の不整合である。保存済み3作品では利用者が `Initialize story project` commit を手動作成して回避しており、その commit は状態、要求、設定、`.gitignore` の4ファイルを含む。

#### 修正方針

`init` の成功条件に、scaffold 全体の初期 commit 作成を加える。既存 Git repository と新規 repository の双方で、stage 前の状態と commit 対象が scaffold の既知集合に完全一致することを検査する。Git identity 不足や commit 失敗時は、作成物を暗黙に削除せず、終了コード5と設定方法・手動 commit 方法を案内する。初期 commit 後は作業ツリーが clean であり、利用者が要求0000を編集した差分だけを `run` の開始時 commit に含める。

未追跡 `managed` の一般許可や `state.json` の ignore は、既存作品へ不明な生成物を混入させ、状態の履歴性を失うため採用しない。

### I-02: 標準作成の推測 `targets` が要求解釈を失敗させる

#### 契約マトリクスと原因

`parse_request_interpretation` へ API 非依存の応答を与え、要求種別と明示有無を比較した。

| 要求 | planner の `targets` | 現在の結果 | 実際の範囲決定 |
| --- | --- | --- | --- |
| 初回作成、パスなし | 推測した `concept.md` | 完全一致検査で失敗 | ファイルと状態から `create_concept` |
| 初回作成、`concept.md` 明示 | `concept.md` | 成功 | 同上 |
| 継続、パスなし | 推測した次成果物 | 完全一致検査で失敗 | ファイルと状態から標準工程 |
| 修正、パス明示 | 明示パス | 成功 | 明示パスを変更 |
| 修正、パスなし | 推測パス | 完全一致検査で失敗 | 対象不明として停止すべき |

`determine_work_scope` は `create`、`continue`、`answer` の `targets` を使わず、状態と実ファイルから次の標準工程を決める。それにもかかわらず parser は kind に関係なく全 target が要求本文の部分文字列であることを要求する。prompt は「推測対象を ambiguities へ」と指示するが、初回作成の自然な出力としてモデルが `concept.md` を補うと、意味上不要なフィールド違反だけで generation 枠を消費する。3作品で同じ失敗になったことから、モデル固有の偶発事象ではなく契約設計上の脆弱性である。

#### 修正方針

- `create`、`continue`、`answer` では `targets=[]` を正規契約にする。モデルが非空 target を返しても、標準範囲には使用せず空へ正規化し、再生成理由にはしない。実際の対象は `WorkScope.targets` を報告する。
- `modify`、`add`、`reconsider` と target を伴う `mixed` では、要求本文に明示した安全な作品ルート相対パスを必須とする。欠落、推測、管理対象外、状態・要求ファイルの直接変更は従来どおり人間判断で停止する。
- prompt と JSON Schema に kind 別の期待を明記し、モデルが標準要求で target を補いにくくする。ただし安全性は prompt に依存せず parser と `determine_work_scope` で保証する。
- 「第1話」など番号だけの修正要求を `episodes/0001.md` へ暗黙変換しない。誤った既存成果物の上書きを避けるため、パス追記を案内する。

この分離により、推測値は標準作成の進行を妨げず、既存成果物を変更する要求では引き続き完全な明示を必要とする。

### I-03: failed run の要求改訂が実行記録と不整合になる

#### 再現と原因

3作品の request 0000 について、run の `request_sha256` と現在の `requests/0000.md` を再計算した hash はすべて不一致だった。例として orbital_lighthouse は記録値 `caedf3c8407b...` に対して実ファイル `692c064545d5...` である。後者は再開 step の `input_hashes` にだけ現れる。

- `select_request` は `active_request` があれば、要求の内容や hash に関係なく `resume` を返す。
- `prepare_run` の resume 分岐は run を読み、status を running に戻すだけで、要求 hash の照合、開始時入力 commit、`request_sha256` 更新をしない。
- `resume_run_record` は最初の `started_at` と累積 `call_counts` を保つが、プロセス単位の再開回数を記録しない。
- failed の終了処理も `_next_request` を呼ぶため、空の次要求テンプレートが作られる。再開時は active request が常に優先され、利用者がその次要求へ具体的内容を書いても検査されない。
- `start_commit` は初回実行境界として不変である。再開前に要求修正を手動 commit しても、その commit と改訂 hash を run に対応付ける欄がない。

現行詳細仕様の「要求 hash が一致しなければ停止」は実装されていない。一方、本文長の縮小など failed run の原因を取り除く要求改訂は実運用上必要であり、単純な変更拒否では再開不能になる。受け入れた最新版だけで `request_sha256` を上書きする案も、どの要求で過去の工程を実行したかを失う。

#### 修正方針

run schema を後方互換に読み込める version 2 へ拡張する。

- `start_commit` と `started_at` は初回値を不変にする。
- `request_sha256` は現在受け入れている要求の hash とし、`validate` が実ファイルと照合する。
- `request_revisions` に初回および改訂ごとの `sha256`、入力 commit、受入時刻、適用開始 step を保存する。既存 schema version 1 は `request_sha256` と `start_commit` から初回要素を補う。
- `resume_count` を追加し、プロセス再開ごとに1増やす。論理 LLM 呼出しの `call_counts` と `model_attempts` は従来どおり累積し、改訂前後を revision 番号で識別できるようにする。
- 要求が変わった場合は、未コミットなら要求と許可された設定だけを完全一致検査して resume 入力 commit に保存する。すでに commit 済みなら現在の HEAD を revision 境界として記録する。
- 入力 hash が変わった工程と全依存工程は再実行対象に戻す。少なくとも要求解釈と範囲決定は必ず再実行し、採用済み成果物は hash 一致時だけ再利用する。
- 自動作成した後続要求はテンプレートまたは実質空である場合だけ共存を許す。具体的内容があれば、active run の改訂か新規要求かを利用者に選ばせ、暗黙に無視しない。

これにより要求変更を明示的な改訂として受け入れつつ、初回境界、最新版、再開回数、各工程入力の監査可能性を同時に保つ。

### I-04: 本文と知識更新の複合工程が失敗理由を隠す

#### 検証境界ごとの再現

既存の API 非依存テストへ個別に入力し、次の境界を再現した。

| 境界 | 決定的な失敗条件 | 現在の再試行・終了 |
| --- | --- | --- |
| 本文 JSON | object 外、欠落・未知キー、別話 path、切断 JSON | writer へ本文全体を最大 generation 枠まで再生成させる |
| Markdown 機械検査 | 必須見出し欠落・重複・順序、未知見出し、残留 fence/comment、JSON 本文 | writer へ本文全体を再生成させる |
| 文字数 | 目標±既定20%の範囲外 | warning のため単独では不採用にしない。reviewer が内容と合わせて判断する |
| 構造化評価 | 評価 JSON、必須 score、issue schema の不備 | reviewer へ評価全体を再生成させる |
| 知識更新 JSON | canon/人物状態のキー・型・source 不備 | reviewer へ更新全体を再生成させる |
| evidence | 本文節内で同一文字列が0件または複数件 | reviewer へ更新全体を再生成させ、枠切れで本文工程全体を failed にする |

特に evidence は安全側の検証として有効だが、改行、空白、括弧・引用符の表記差だけで0件になり、短い台詞や人物名では複数件になりやすい。テストで、本文外文字列と本文内の非一意な短語がともに拒否されることを確認した。

#### 保存データから確定できる範囲

3作品すべての最初の本文試行は、本文候補が review で採用可能になった後、knowledge 用 reviewer を複数回呼び、`採用本文から canon・人物状態更新候補を有効な形式で検証できませんでした` で終わった。gravity_garden と memory_fleet の別試行では writer を3回呼んだ後に `有効な本文候補を生成できませんでした` となった。

run JSON は各再生成の検証 code や sanitized reason を保存せず、すべての completion を `completed` とだけ記録する。生のモデル応答も意図どおり保存していないため、実運用試行について JSON 構文、見出し、evidence のどれだったかをこれ以上断定できない。これは調査不能条件であり、観測性の欠陥でもある。また knowledge の purpose は `record_model_attempt` で未知 category として `generation` に変換され、集計上 writer generation と区別できない。

#### 修正方針

- 応答本文を保存せず、検証境界、検証 code、試行番号、候補 hash、sanitized reason を試行記録へ残す。
- 本文 JSON、機械検査、評価、knowledge を別 step として記録し、`knowledge` を generation へ畳み込まない。
- evidence は空白・改行だけを正規化して一意な元本文範囲へ逆引きし、保存時は元本文の完全一致文字列へ置換する。表現の言い換えや曖昧な複数一致は引き続き拒否する。
- 不正な knowledge 項目を項目単位で診断し、本文候補そのものの再生成理由にはしない。成果保全と再開方法は次項で定める。

### I-05: 採用可能な本文を knowledge 失敗時に失う

#### 原因と追加発見

`produce_draft` は本文生成、機械検査、評価、knowledge 抽出を1回の関数呼出し内で行う。`best` が存在しても knowledge 抽出が枠切れになると status `failed` を返す。統合層は `best` の有無だけで一時的な `documents` を組み立てるものの、実行層は status が failed なら全 documents を空にするため、本文候補・評価・hash はどこにも保存されない。

加えて `DraftKnowledgeUpdate` は抽出成功時も `WorkflowExecution.documents` へ変換されず、`canon.md` と `characters.md` へ適用されない。つまり高コストな必須ゲートでありながら、現在は成功結果を破棄している。

#### 永続化案の比較

| 案 | 成果保全 | 下流の整合性 | 採用 |
| --- | --- | --- | --- |
| 失敗時も本文を `episodes/` へ即採用 | 高い | knowledge 未反映の本文を下流が採用済みと誤認する | 不採用 |
| run JSON に本文全体を格納 | 高い | run の肥大化、報告・検証責務の混在 | 不採用 |
| hash で束縛した内部 checkpoint | 高い | 正式採用前として隔離できる | 採用 |
| 現状どおり再生成 | なし | 一貫するが費用・時間が過大 | 不採用 |

#### 採用設計

`.story-pipeline/checkpoints/NNNN/draft.json` を管理対象として追加し、次を保存する。

- schema version、要求番号・revision、対象話 path
- 要求、解釈、設定・canon・style・計画・前後話の入力 hash
- 正規化済み本文、本文 hash、機械検査結果
- 採用評価と評価対象 hash、生成・評価のモデル参照、作成時刻
- knowledge 状態（pending/completed）、検証済み更新候補とその hash

本文が採用可能になった直後に checkpoint を atomic write し、run 進捗と failed 終了 commit の対象へ含める。再開時は全入力 hash と候補 hash が一致した場合だけ writer と本文 reviewer を省略し、`extract_knowledge` から再開する。不一致なら古い checkpoint を診断付きで無効化するが、自動削除せず、新しい revision の checkpoint と区別する。

knowledge 検証完了後に、本文、canon、人物状態を一つの採用単位として atomic write し、state 更新と終了 commit に含める。適用後の各出力 hash を記録してから checkpoint を `adopted` にする。途中クラッシュ時は hash から未適用・全適用・部分適用を判定し、部分適用を自動で進めず復旧を案内する。

これにより本文生成と knowledge 抽出は独立した再開可能 step になり、knowledge の一時的失敗で本文の再生成を要求しない。

### I-06: 実行中の無出力と失敗分類不足

#### 現在の経路

- transport は timeout/connection を `temporary`、HTTP 429を `rate_limit`、`finish_reason=length` を `output_truncated`、不正本文を `invalid_response` に分類する。
- client は transport 再試行とモデル fallback を持つが、通知 callback の既定値は何もしない。`prepare_run` は CLI 出力へ callback を接続しないため、待機・再試行は表示されない。
- workflow の JSON/機械検査失敗は論理呼出しループ内で再生成するが、開始、失敗理由、残り枠を表示・永続化しない。
- run step は呼出し前に保存されるので別プロセスから `status` を見れば大区分だけは分かるが、通常の `run` は非 streaming HTTP 完了まで無出力である。
- `output_truncated` はモデル fallback 対象だが同一モデルの transport 再試行対象ではない。単一モデル構成では即 failed となる。実運用の memory_fleet でこの分類を確認した。
- 予期しない例外は実行層で終了コード9と一般文言へ変換され、例外型・安全な発生位置・incident ID が残らない。

#### 診断・進捗契約

CLI の stderr と run JSON に、同じ構造化 event を出す。event は `timestamp`、`request`、`step`、`purpose`、`role`、`logical_attempt/current_limit`、`transport_attempt/current_limit`、`model_reference`、`state`（started/waiting/retrying/completed/failed）、`failure_kind`、`wait_seconds`、`elapsed_ms`、`candidate_hash` を許可し、prompt、応答本文、HTTP header、URL query、環境変数値は許可しない。すべての文字列を `SecretSanitizer` に通す。

表示例は `request 0004 · draft_generate · writer · logical 2/3 · started` のような1行とし、呼出し開始時、30秒ごとの heartbeat、transport 待機、検証再生成、終了時に flush する。heartbeat は別 API 呼出しを行わず、同じ行を過剰に増やさない。

失敗は次の階層を保つ。

1. transport attempt: timeout、rate limit、HTTP一時障害、認証等
2. logical attempt: output truncated、invalid response、JSON/schema、mechanical、evidence
3. workflow exhaustion: generation/review/revision/knowledge の上限枯渇
4. process incident: 予期しない例外、割込み、永続化・Git失敗

終了メッセージには停止 step、最終 failure kind、使用枠/上限、保存済み checkpoint、`story-pipeline run` で再開できるか、`validate` が必要かを必ず示す。予期しない例外は応答・秘密を含まない例外型と内部 component、UUID incident ID だけを run に保存し、通常表示では traceback を出さない。

### I-07: 最終話から章改稿・全体改稿へ遷移しない

#### 再現と原因

保存済み3作品の `chapters/0001.md` は `## 収録話` に `0001` だけを持ち、本文0001は存在して `completed_episodes=[1]` である。それでも状態は共通して `phase=episode_planning`、`current_chapter=1`、`next_chapter=1`、`next_episode=2`、`completed_chapters=[]` となる。

`workflow_executor` の drafting 分岐が、章計画を読まず常に次を返すことが直接原因である。

- `completed_episodes` に対象番号を追加
- `next_episode` を対象番号+1以上へ増加
- `phase` を無条件に `episode_planning` へ設定

次の標準範囲決定は episode 0002 の話計画作成を選ぶが、`find_episode_chapter` は0002を収録する章を見つけられないため、章改稿に到達できない。状態 validator は `next_episode` が完了済み最大より大きいことしか検査せず、`current_chapter` の収録話集合との関係を検証しない。

さらに chapter revision 分岐は `produce_chapter_revision(..., all_chapters_complete=False)` の既定値を常に使う。単体 workflow には全章完了時の `final_revision` 遷移テストがあるが、統合層が全章集合を計算して引数を渡さないため、実際の run では最後の章から全体改稿へ進めない。

#### 修正方針

状態遷移を成果物の存在だけでなく、検証済み章・話対応表から一箇所で計算する。

1. 全 `chapters/NNNN.md` の `## 収録話` を parse し、章番号順、話番号の一意性、連続性、重複・欠落を検証する。
2. 本文採用後、その章の未完了話があれば最小番号を `next_episode` とし `episode_planning` へ戻す。
3. 章内全話が完了していれば `phase=chapter_revision`、`current_chapter` は現在章のままにする。`next_episode` は全体で次に予定された話、存在しなければ最終話+1の sentinel とする。
4. 章改稿完了後、`completed_chapters` へ追加する。未完了章があれば、その章と最初の収録話を `current_chapter` / `next_chapter` / `next_episode` に設定して `episode_planning` へ進む。
5. 全章完了なら `phase=final_revision`、`current_chapter=null` とする。章 workflow へ外部 bool を渡すのではなく、同じ対応表と完了集合から決定する。

`validate` と `status` に、収録話の重複・欠落、phase と現在章の不一致、章内全話完了なのに章改稿でない状態、未完了話を飛ばす `next_episode`、全章完了なのに全体改稿でない状態を追加する。既存3作品は対応表から安全に `phase=chapter_revision`、`next_episode=2` へ移行できるが、自動 migration は hash と Git clean を確認した明示コマンド内だけで行う。

### I-08: 終了コード9の診断情報が消える

#### 境界別の挙動

API 非依存の fake client が planner 呼出しで `RuntimeError` を送出する条件を作ると、終了コード9、run status `failed`、resume step `interpret_request` を再現した。run と CLI の reason は `予期しない内部エラーが発生しました` だけになり、例外型と安全な component は失われた。処理報告と終了 commit は作成され、lock は `finally` で解放された。

| 境界 | 現在の処理 | 欠落・危険 |
| --- | --- | --- |
| `execute_started_run` 内 | `Exception` を捕捉し failed run と終了コード9へ変換 | 例外型・component・incident IDを破棄し、すべて retryable=true |
| 報告生成・終了 commit・次要求作成 | `run_command` の `finally` で lock を解放後、例外を外へ送出 | run が completed なのに commit/report がない等の終了段階を記録できない |
| CLI 最外層 | 全 `Exception` を同じ3行と終了コード9へ変換 | run 開始前後の区別、復旧方法、既存 incident 参照がない |
| Git subprocess | stderr を破棄し、失敗を多くは終了コード5の一般 Git error に変換 | return code と安全な command component が残らない |
| lock release | 所有権不一致・unlink 失敗を終了コード9にする | 元の処理例外がある場合、解放例外で上書きされ得る |

保存済み3作品の run schema には process exit code と incident event がなく、外部実行ログも保存されていない。そのため、報告された終了コード9が上表のどこで発生したかは再現不能であり、これ以上の根本原因は断定しない。

#### 修正方針

- run 全体を `starting / executing / finalizing / committed` の lifecycle として記録し、終了処理の各段階も atomic に進捗保存する。
- 未知例外は `incident_id`、例外クラス名、固定 component ID、現在 step、lifecycle、retryable=false を秘密除去後に保存する。例外本文と traceback は既定で保存しない。
- CLI 最外層は既存 incident があれば同じ ID と停止位置を表示し、なければ開始前 incident として stderr に ID を出す。
- lock 解放失敗は元の incident を保持したまま secondary incident として表示する。所有権を確認できない lock は従来どおり自動削除しない。
- Git helper は許可済み subcommand 名、return code、stderr の秘密除去済み先頭だけを incident event に残す。引数のパス・commit 対象は既存の正規化済み相対パスだけを扱う。
- SIGINT/SIGTERM は未知例外と分け、running step を `interrupted` 相当で回復可能に閉じる。強制終了で記録できない場合は次回起動時に lock と running run から復元する。

### I-09: token・時間・再試行を測定できない

#### 原因

`ChatTransport._parse_success` は content、model、finish_reason だけを返し、API の `usage` を破棄する。client は transport 試行の合計数しか `CompletionResult` に返さず、各試行の時刻、失敗分類、待機を保持しない。さらに実行層は workflow 全体が戻った後に各 completion を順に記録し、その時点の同じ timestamp を started/finished の両方へ設定する。このため保存済み本文 run の多数の呼出しが同一秒・所要0秒に見える。

#### run schema version 2 の呼出し契約

`model_calls` を論理呼出し単位の配列とし、開始時に running record を atomic 追記し、各 transport 試行と終了を逐次更新する。

```json
{
  "id": "draft_generate-0002",
  "step": "draft_generate",
  "purpose": "draft",
  "logical_attempt": 2,
  "logical_limit": 3,
  "role": "writer",
  "model_reference": "default",
  "api_model": "provider/model",
  "started_at": "RFC3339 UTC",
  "finished_at": "RFC3339 UTC or null",
  "elapsed_ms": 1234,
  "wait_ms": 500,
  "result": "completed|failed|interrupted",
  "failure_kind": null,
  "finish_reason": "stop",
  "max_output_tokens": 16384,
  "usage": {
    "input_tokens": 100,
    "output_tokens": 200,
    "total_tokens": 300,
    "cached_input_tokens": null,
    "reasoning_tokens": null,
    "source": "provider"
  },
  "transport_attempts": [],
  "fallbacks": []
}
```

各 `transport_attempts` はモデル参照、試行番号、開始・終了時刻、単調時計由来 `elapsed_ms`、result、HTTP status（取得時だけ）、failure kind、`retry_after_ms` と実待機 `wait_ms` を持つ。API 応答に usage がない場合は token 値を推測せず `null`、source `unavailable` とする。provider が返す prompt/completion/total token を input/output/total へ正規化し、cached・reasoning の内訳は存在する場合だけ保存する。

`output_truncated` は成功 completion ではなく failed 論理呼出しとして、finish_reason、受信済み output token、設定上限を保存する。fallback は source/target/reason/発生時刻を該当 call に保持する。run 上位には `call_counts` を互換用集計として残し、`transport_attempt_count`、`retry_wait_ms`、token 合計を `model_calls` から再計算して validate する。

時刻は表示用 RFC3339 と所要時間用 monotonic clock を分ける。再開後も ID を一意にし、request revision と resume count を各 call に関連付ける。prompt、response content、API key、Authorization、完全 URL はこの schema に含めない。

## 回帰試験計画

### API 非依存マトリクス

| 領域 | 正常系 | 安全停止・障害系 | migration・回復 |
| --- | --- | --- | --- |
| 初期導線 | init→要求編集→fake run | identity 不足、既存差分、未追跡 managed、推測修正 target | 初期 commit 直後と要求 commit 後の Git 集合 |
| 再開 | unchanged/未commit/commit済み要求 | 具体的な後続要求、改変出力、欠落開始 commit | schema v1→v2、改訂別依存 step 巻戻し |
| 本文 | JSON、見出し、文字数warning、評価、knowledge適用 | 切断、schema、非一意 evidence、部分適用、checkpoint改変 | knowledge step だけ再開、入力変更時無効化 |
| 状態 | 1章1話、1章複数話、複数章、completed | 収録話重複・欠落・逆順、9999、phase矛盾 | 保存済み3作品相当を章改稿へ移行 |
| 観測性 | usage有/無、retry/fallback、heartbeat | truncation、timeout、例外、Git/lock失敗、秘密fixture | interrupted run 復旧、集計再計算 |

各セルを fake clock、fake transport、temp Git repository で検査する。乱数と時刻を固定し、ネットワーク、`~/.env`、実 API key に依存させない。全 unit/integration テスト、distribution wheel テスト、`validate` fixture を CI 必須とする。

### OpenRouter 3作品統合・性能試験

OpenRouter は非 streaming 応答にも native tokenizer による token と cost を含む `usage` を自動返すため、価格表の固定値ではなく各応答の実課金値を集計する。仕様根拠は [OpenRouter Usage Accounting](https://openrouter.ai/docs/cookbook/administration/usage-accounting) と [API Reference](https://openrouter.ai/docs/api/reference/overview) とする。

#### 固定条件

- base URL: `https://openrouter.ai/api/v1`
- API key: `~/.env` の `OPENROUTER_APIKEY`。値を出力・fixture・Gitへ保存しない。
- model: 全 role で `deepseek/deepseek-v4-flash:nitro`
- 3作品: 同じ1章1話、本文2,000〜3,000字、読切条件で、題材・人物・禁止事項だけを変える。
- temperature 0、reasoning effort none、max tokens 16,384、transport retry 2。作品は順次実行し、並列にしない。
- 公開 wheel を一時環境へ install し、各作品を別の `/tmp` Git repository で `init` から `completed` まで実行する。

#### 手順

1. API 非依存全テスト、wheel install、秘密 scanner を通す。失敗時は実 API を呼ばない。
2. 1作品目を構想から完成まで標準要求だけで実行し、各 run 後に `validate`、Git status、run schema、usage、cost を検査する。
3. 予算・成功条件内なら2、3作品目を順次実行する。要求修正、手動成果物修正、設定上限の途中緩和を成功のために行わない。
4. 各作品で本文 checkpoint、章改稿、全体改稿への遷移と、最終 `completed` を確認する。
5. model call ごとの所要、待機、token、cost、呼出し数と作品別合計を秘密なし JSON/Markdown に出力する。

#### 費用・呼出しの停止条件

- 3作品合計 cost 上限 USD 5.00、1作品上限 USD 2.00、上限接近停止閾値は合計 USD 4.00 とする。
- 各応答の `usage.cost` を加算し、閾値到達後は次の論理呼出しを開始しない。単一呼出しによる超過も試験失敗として記録する。
- 1作品の論理 model call は30以下、writer 本文生成は2以下、transport attempt は論理 call の1.2倍以下を受入条件とする。上限超過時は要求や設定を変えて継続しない。
- usage/cost が欠落した呼出しが1件でもあれば費用計測不能として後続作品を開始しない。

#### 成功・性能判定

- 3/3作品が初回要求の追記や failed resume なしに `phase=completed` へ到達し、各 `validate` が error 0である。
- Git は CLI が作る空の次要求以外 clean で、全 run/report/output/checkpoint の対応と hash が一致する。
- 全呼出しの input/output/total token、cost、開始・終了・所要、transport attempt、待機が非欠落である。
- 1作品20分以下、3作品合計60分以下、単一の無出力区間30秒以下とする。heartbeat 自体は所要時間に含める。
- knowledge 再試行が起きた場合も同じ本文 hash を使用し、writer 本文再生成0回で回復する。truncation、終了コード9、秘密漏洩、部分適用は1件でも失敗とする。
