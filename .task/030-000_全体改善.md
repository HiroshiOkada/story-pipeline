# 全体改善

## 背景

コードベース全体(約1.4万行)を対象に、コード品質・テスト・ドキュメント整合・エラーメッセージの4観点で改善余地を調査した。主な発見は次のとおり。

- 実害バグ2件: Git 競合状態の誤判定(`git_validation.py` の unmerged レコード処理)、変更行数上限の境界ずれ(仕様は 0..999 行許可・1000 行以上で停止だが、実装は 999 行で停止)。
- エラーメッセージの構造的問題: 最重要経路である `run` 実行中のエラーで復旧案(action)と箇所(location)が表示されない、終了処理の失敗で終了コードが一律 9 に潰れる、LLM/API エラーが provider の英語生メッセージのまま届く、内部用語(state キー名・stale・scaffold 等)がむき出し、state.json の直接編集を促す復旧案が仕様と矛盾。
- ドキュメント陳腐化: specification.md が python-dotenv 使用・旧設定例・旧 state 例を載せたまま、check-llm がサブコマンド一覧にない、scaffold 構成の記述が実装と不一致、README に誤記。
- テストの穴: state.py / config.py の検証不正系がほぼ未テスト。
- 大規模な構造的重複: 7フェーズの workflow 群で生成→検査→評価→改稿ループがコピー実装されている(約1200行規模)。

## 作業目標

利用者(作家)が直面する実害バグを修正し、エラーメッセージを「何が起きたか」「次に何をすればよいか」が分かる水準へ引き上げ、仕様書・取扱説明書と実装を一致させ、中核の検証ロジックにテストを補強する。

## 完了条件

- Git 競合状態で `run` / `validate` が正しく「競合を解消する必要があります」と報告する。
- 変更行数の上限判定が仕様どおり(0..999 行は処理、1000 行以上で確認待ち)に動く。
- `run` のあらゆる失敗経路で復旧案が表示され、終了コードが原因に対応する。
- LLM/API 由来の失敗が日本語の案内付きで表示される。
- 仕様書・README・取扱説明書の記述が実装と一致する。
- state / config 検証の不正系テストが追加され、全テストが成功する。

## 今回の対象外(後続フェーズ候補)

調査で見つかったが、規模・リスク・仕様判断を要するため別フェーズへ切り分ける。

- workflow 群の共通化(ジェネリックな生成→評価→改稿エンジン化): 約1200行の重複解消は大規模リファクタであり、統合テストを伴う独立フェーズで実施する。
- `run_*_revision_loop` 7関数のデッドコード化の扱い: workflow 共通化の方針と一体で決める。
- decision 解決フロー(`PlannedRequest.decisions` / `human_decision`)の未完機能: 仕様確認を伴う機能開発。
- `summarizer` role / `summary_calls` limit の未使用問題: 仕様判断が必要。
- テスト基盤整備(FakeClient 共通化、応答ビルダー統一): 上記リファクタと合わせて実施する。
- ValueError → StoryPipelineError 置換方針の明文化、終了コード定数の集約。
