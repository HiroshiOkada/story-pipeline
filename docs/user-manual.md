# Story Pipeline 取扱説明書

この文書は、Story Pipeline を使って新しい小説プロジェクトを始め、AI と対話しながら完成まで進めるエンドユーザー向けの説明書です。

## この説明書の読み方

- 初めて使う場合は、「利用前の準備」から順に読んでください。
- 日常の操作だけを確認したい場合は、「基本の制作サイクル」を参照してください。
- 処理が止まった場合は、「トラブル対応」を参照してください。
- 設定や内部形式の厳密な契約は、[詳細仕様](detailed-specification/README.md)を参照してください。

## 対象機能

| 利用場面 | 使用するもの | 主な結果 |
| --- | --- | --- |
| 新規作品を作る | `story-pipeline init` | 作品用ディレクトリと初期 Git commit |
| 制作状況を知る | `story-pipeline status` | 現在のフェーズと次の標準処理 |
| 問題を調べる | `story-pipeline validate` | 設定、ファイル、状態、Git の検査結果 |
| 要求を処理する | `story-pipeline run` | 作品成果物、報告、実行記録、Git commit |
| 旧状態を直す | `story-pipeline migrate-state` | 安全条件を満たす場合だけ状態を移行 |
| 壊れた進行状態から復旧する | `story-pipeline recover --abandon-active` | 未記録情報を保全して新規要求を受理できる状態へ復旧 |

## 1. 利用前の準備

### 1.1 必要なもの

- Python 3.12 以上
- Git
- OpenAI Chat Completions 互換 API を利用できるアカウントと API キー
- Markdown と JSONC を編集できるテキストエディター

Story Pipeline はデスクトップ画面を持たない CLI です。ターミナルからコマンドを実行し、人間の要求と作品を Markdown ファイルで管理します。LLM サービスの利用料は Story Pipeline ではなく、設定した API provider から請求されます。

### 1.2 Git の初期設定

Story Pipeline は制作の節目を自動的にローカル Git commit へ保存します。初回利用前に、Git の名前とメールアドレスを設定してください。

```console
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
```

既に設定済みなら再設定は不要です。Story Pipeline 自体はブランチ作成、リモートへの push、履歴の書き換えを行いません。

### 1.3 API キーの扱い

API キーは設定ファイルへ直接書かず、環境変数または `.env` に保存します。作品ディレクトリの `.env` は初期状態から Git の除外対象です。

```dotenv
OPENAI_API_KEY=your-api-key
```

次の点を守ってください。

- API キーを要求 Markdown、作品ファイル、設定の `parameters` に書かない。
- `.env` を `git add -f` などで追跡しない。
- エラー報告を共有する前に、独自に追加したファイルへ秘密値がないか確認する。

## 2. 導入と更新

### 2.1 リポジトリから導入する

PyPI 公開前は、配布元のリポジトリを取得してインストールします。

```console
git clone <repository-url>
cd story-pipeline
python -m pip install .
story-pipeline --version
```

`story-pipeline 0.1.0` のようにバージョンが表示されれば導入完了です。コマンドが見つからない場合は、Python をインストールした環境と同じ環境で実行しているか、Python の scripts ディレクトリが `PATH` に含まれているか確認してください。

### 2.2 仮想環境を使う場合

作品ごとではなく Story Pipeline のツール用に仮想環境を作ることもできます。

```console
python -m venv .venv
source .venv/bin/activate
python -m pip install .
```

Windows PowerShell では有効化コマンドが `.venv\Scripts\Activate.ps1` になります。以後の `story-pipeline` は仮想環境を有効にしたターミナルで実行します。

### 2.3 更新前の注意

更新前に作品プロジェクトで `git status` と `story-pipeline validate` を実行し、バックアップまたはリモートへの push を済ませることを推奨します。更新後、旧版で作成した作品に状態移行が必要と案内された場合だけ `migrate-state` を使用してください。

## 3. 新しい作品の初期化

### 3.1 空のディレクトリを用意する

```console
mkdir my-story
story-pipeline init my-story
cd my-story
```

成功すると、絶対パス、最初の要求ファイル、次のコマンドが表示されます。`init` の対象は空のディレクトリ、または差分のない空の Git repository でなければなりません。既存ファイルを含むディレクトリへ上書き初期化はしません。

現在の空ディレクトリを初期化する場合は次のようにします。

```console
story-pipeline init
```

### 3.2 初期化で作られるもの

```text
my-story/
├── .git/
├── .gitignore
├── .story-pipeline/
│   ├── runs/
│   └── state.json
├── chapters/
├── episode_plans/
├── episodes/
├── requests/
│   └── 0000.md
└── story-pipeline-config.jsonc
```

初期化時には `.gitignore`、状態、最初の要求、設定の4ファイルだけが `Initialize story project` という commit に保存されます。空の成果物ディレクトリは、ファイルができるまで Git には記録されません。

### 3.3 初期化に失敗した場合

Git identity が未設定などの理由で commit だけが失敗しても、作成済みの scaffold は保持されます。画面の `Action:` に従い、Git identity を設定してから、案内された4ファイルだけを手動で commit してください。既存のファイルがあるというエラーでは、別の空ディレクトリを用意してください。

## 4. API とモデルの設定

### 4.1 初期設定

`story-pipeline-config.jsonc` はコメントと末尾カンマを許す JSONC です。初期状態では OpenAI の `gpt-5.6-luna` を全役割で使用します。従来の非 reasoning 相当の速度とコスト特性を維持するため、`reasoning_effort` は `none` に設定します。

```jsonc
{
  "config_version": 1,
  "dotenv": {
    "files": ["~/.env", ".env"]
  },
  "providers": {
    "openai": {
      "base_url": "https://api.openai.com/v1",
      "api_key_env": "OPENAI_API_KEY"
    }
  },
  "models": {
    "default": {
      "provider": "openai",
      "model": "gpt-5.6-luna",
      "parameters": {
        "reasoning_effort": "none"
      }
    }
  },
  "roles": {
    "planner": ["default"],
    "writer": ["default"],
    "reviewer": ["default"],
    "reviser": ["default"],
    "summarizer": ["default"]
  }
}
```

設定を編集したら、API を呼び出す前に検査します。

```console
story-pipeline validate
```

### 4.2 provider と model

- `providers`: API の接続先と、API キーを読む環境変数名を定義します。
- `models`: provider と API 上のモデル識別子を組み合わせます。
- `roles`: 制作上の役割ごとに、使用するモデル定義名を優先順で並べます。

OpenAI Chat Completions 互換サービスを使う場合は、そのサービスが案内するベース URL、API キー環境変数、モデル識別子へ置き換えます。ベース URL は通常 `/v1` までで、`/chat/completions` は Story Pipeline が付加します。

`models.<name>.max_tokens` はモデルが生成する最大トークン数です。省略時は `131072` です。サービスやモデルの上限を超えない値へ調整してください。温度などは `parameters` に指定できますが、`model`、`messages`、`max_tokens`、URL、認証情報は指定できません。

### 4.3 役割とフォールバック

| role | 用途 |
| --- | --- |
| `planner` | 構想、設定、構成、話計画 |
| `writer` | 本文の執筆 |
| `reviewer` | 要求適合、品質、整合性の評価 |
| `reviser` | 評価に基づく改稿 |
| `summarizer` | 報告や知識更新に必要な要約 |

各 role の配列に複数モデルを書くと、前の候補が一時障害や利用不能になった場合に後の候補を試します。すべての role は必須ですが、同じモデルを共有できます。

### 4.4 dotenv の読込順

`dotenv.files` は左から順に読みます。プロセス起動時に既に存在する環境変数が最優先で、先に読み込まれた値を後のファイルで上書きしません。初期値の `["~/.env", ".env"]` なら、優先順位は次のとおりです。

1. ターミナルで設定済みの環境変数
2. ホームディレクトリの `~/.env`
3. 作品ルートの `.env`

ファイルが存在しないだけなら警告ですが、必要な API キーがどこにもなければ実行できません。検査結果に値そのものは表示されません。

### 4.5 回数、通信、変更量の制限

| 設定 | 初期値 | 意味 |
| --- | ---: | --- |
| `generation_calls` | 3 | 1要求内の生成呼び出し上限 |
| `review_calls` | 3 | 評価呼び出し上限 |
| `revision_calls` | 3 | 改稿呼び出し上限 |
| `summary_calls` | 3 | 要約呼び出し上限 |
| `retry_calls_per_request` | 2 | 1つの論理呼び出しで許す通信再試行上限 |
| `max_changed_lines` | 999 | 確認なしで変更できる管理ファイル行数 |
| `timeout_seconds` | 120 | HTTP タイムアウト秒数 |
| `retry_attempts` | 3 | 通信試行総数 |

値を増やすと品質改善や長い生成に余裕が出る一方、費用と待ち時間も増える可能性があります。`max_changed_lines` は安全上の判定値で、初期設定では変更行数が999行までの作品変更はそのまま適用され、1000行以上になる作品変更は適用されず人間の確認待ちになります。

## 5. 最初の要求を書く

`requests/0000.md` の HTML コメントを参考に、Markdown の各欄へ希望を書きます。コメントは説明用なので、本文を書いた後に残っていても構いません。ただし、コメントしかない要求は内容不足として停止します。

```markdown
# 作品作成要求

## 作りたい作品

近未来の瀬戸内海を舞台にした、全6話の青春ミステリー。
高校生以上を想定し、1話あたり約4,000字。

## 必須条件

- 主人公と幼なじみの関係修復を物語の軸にする。
- 謎の手掛かりは解決前に公平に提示する。
- 三人称一元視点で書く。

## 禁止事項

- 超自然的な解決を使わない。
- 実在する個人をモデルにしない。
```

### 5.1 良い要求に含める情報

- ジャンル、中心的な着想、想定読者
- 全体の話数や文字数など、希望する規模
- 主人公、舞台、結末など譲れない条件
- 視点、文体、表記の希望
- 暴力表現など避けたい内容
- 判断を AI に任せてよい部分

すべてを決める必要はありません。根本を左右しない不足は AI が仮定し、成果物と報告に記録します。一方、必須条件同士が矛盾する場合や、根本方針を推測で決められない場合は人間の判断待ちになります。

### 5.2 追加資料を含める場合

通常は要求本文だけで開始してください。別ファイルを開始時 commit に含めたい場合は、要求に「追加資料として次のファイルを開始時コミットに含める」と明記し、作品ルートからの相対パスをコード表記します。

```markdown
追加資料として次のファイルを開始時コミットに含める: `references/setting-notes.md`
```

絶対パス、glob、ディレクトリ、シンボリックリンク、秘密を含むファイル、CLI 管理ファイルは指定できません。

## 6. 基本の制作サイクル

### 6.1 実行前に確認する

作品ルート、またはその配下のディレクトリで次を実行します。

```console
story-pipeline validate
story-pipeline status
```

`validate` が `Validation passed.` または警告だけで終了し、`status` の `Next action` が期待どおりなら実行できます。警告は必ずしも停止理由ではありませんが、内容を理解してから進めてください。

### 6.2 要求を1件処理する

```console
story-pipeline run
```

`run` は番号が最も小さい未処理要求を1件だけ選びます。要求の意味と現在の制作段階から作業範囲を決め、必要な LLM 呼び出し、評価、改稿、ファイル保存を行います。「そのまま進めてください」という後続要求なら、通常は次の自然な制作単位を進めます。

実行中は標準エラーへ JSON Lines の進捗イベントが出ます。通信開始、再試行、モデルのフォールバック、30秒ごとの heartbeat を確認できます。プロンプト、応答本文、API キー、完全な URL は表示されません。

### 6.3 実行後に確認する

実行終了後は次の順で確認します。

1. 画面に表示された status が `completed`、`awaiting_human`、`failed` のどれか確認する。
2. `requests/NNNN_agent.md` の処理報告を読む。
3. 「作成・変更したファイル」に挙がった作品ファイルを読む。
4. `story-pipeline status` と `story-pipeline validate` を実行する。
5. `git log --oneline` と `git status` で保存状態を確認する。
6. 新しく作られた空の `requests/NNNN.md` へ次の要求を書く。

正常な終了後も、次要求ファイルは意図的に未追跡のまま作られます。これは次回の人間入力であり、次の `run` が開始時 commit に保存します。

### 6.4 1回で完成まで進まない理由

Story Pipeline は、人間が各段階の成果を確認して方向を修正できるよう、要求ごと・制作単位ごとに進みます。標準継続の主な順序は次のとおりです。

```text
構想 → 基礎設定 → 全体構成・章計画 → 話計画 → 本文
     → 章内全話の完成 → 章改稿 → 全章の完成 → 全体改稿 → 完成
```

次要求へ「そのまま進めてください」と書けば標準工程を続けられます。複数話を明示的に依頼した場合も、各話の計画、本文、評価、整合更新を終えてから次へ進み、呼び出し回数や変更行数の上限で安全停止します。

## 7. 制作フェーズと成果物

| Phase | 何を行うか | 主な成果物 |
| --- | --- | --- |
| `concept` | 作品の核、読者、規模、条件を定める | `concept.md` |
| `foundation` | 世界、人物、文体、確定事実を整える | `world.md`, `characters.md`, `style.md`, `canon.md` |
| `plotting` | 全体の因果、結末、章と話の構成を作る | `plot.md`, `chapters/NNNN.md` |
| `episode_planning` | 次話を具体的な場面へ分解する | `episode_plans/NNNN.md` |
| `drafting` | 本文を執筆、評価、改稿し、整合情報を更新する | `episodes/NNNN.md`, `canon.md`, `characters.md` |
| `chapter_revision` | 章全体の接続、テンポ、伏線などを評価・改稿する | 章内本文、章あらすじ |
| `final_revision` | 全体の因果、人物変化、伏線、結末を評価・改稿する | 作品全体の更新 |
| `completed` | 明示的な完成判定済み | 完成作品と最終報告 |

### 7.1 人間が読んでよいファイル

- `concept.md`: タイトル、ジャンル、着想、テーマ、規模、条件、仮定
- `world.md`: 舞台、制度、固有ルール、場所、時系列
- `characters.md`: 人物の目的、関係、変化、口調、現在状態
- `plot.md`: 転換点、クライマックス、結末、人物変化、伏線、章構成
- `style.md`: 視点、時制、文体、表記、会話の規則
- `canon.md`: 作中で確定した事実、人物状態、時系列、伏線、用語
- `chapters/NNNN.md`: 各章の目的、開始・終了状態、収録話、接続条件
- `episode_plans/NNNN.md`: 各話の場面、開示、感情変化、伏線、目標文字数
- `episodes/NNNN.md`: 話タイトルと本文
- `requests/NNNN_agent.md`: 人間向けの処理報告

これらを読むことはできますが、要求ファイルと設定以外の CLI 管理ファイルを直接編集する運用は避けてください。追跡済み管理ファイルの手編集は次回実行時に復元されることがあります。変更したい内容は次要求に、対象と意図を具体的に書きます。

### 7.2 内部ファイル

- `.story-pipeline/state.json`: 現在の制作フェーズ、完了話、判断待ちなどの状態
- `.story-pipeline/runs/NNNN.json`: 要求ごとの工程、モデル、通信、usage、失敗情報
- `.story-pipeline/checkpoints/NNNN/draft.json`: 本文評価後、正式採用までの再開用 checkpoint
- `.story-pipeline/run.lock`: 同時実行を防ぐ一時ロック

内部ファイルは通常、読んだり編集したりする必要はありません。問題調査では `status`、`validate`、処理報告を先に使ってください。

## 8. 追加要求と人間の判断

### 8.1 標準の継続

新しい要求テンプレートへ次のように書きます。

```markdown
# 追加要求

そのまま次の標準処理へ進めてください。
```

現在の状態から、未完了の構想、設定、構成、話計画、本文、章改稿、全体改稿のうち最初の対象が選ばれます。

### 8.2 修正を依頼する

対象、変更意図、変更範囲を明確にします。

```markdown
# 追加要求

`characters.md` の主人公・澪の口調を、同級生に対してだけ少し砕けたものに変更してください。
既に確定した経歴と、教師に対する敬語は変更しないでください。
必要なら未執筆話の計画と `style.md` も整合させてください。
```

完成済み本文へ波及する大規模変更、主人公、ジャンル、結末、規模、重要設定の変更は、変更意思と対象範囲を明記してください。影響が大きく一度に安全に適用できない場合は、影響一覧を示して判断待ちになります。

### 8.3 `awaiting_human` への回答

処理報告の「人間に判断してほしい事項」に、判断 ID、質問、影響、選択肢が記載されます。次要求に判断 ID と回答を書きます。

```markdown
# 追加要求

判断 `request-0000-decision-01` への回答: 選択肢Bを採用してください。
理由は、全6話の規模を維持したいからです。
```

判断 ID は実際の報告に記載された値を正確に使ってください。未解決の判断を飛ばして別の後続要求を処理することはできません。

### 8.4 `failed` 後の要求

通信障害などで `failed` になった場合、空の次要求を残したまま、原因を解消して同じ `story-pipeline run` を再実行します。再開情報があれば完了済み工程から続けます。

失敗原因を直すために処理中の要求そのものを編集した場合、その変更は要求の新しい revision として記録されます。空の次要求へ先に具体的な別要求を書いてしまうと、旧要求の改訂か新規要求か曖昧になるため停止します。どちらを優先するか整理してから再実行してください。

## 9. コマンドリファレンス

### 9.1 共通

```console
story-pipeline --help
story-pipeline --version
```

引数なしまたは `--help` はヘルプ、`--version` はバージョンを表示します。通常結果は標準出力、警告とエラーは標準エラーへ出ます。

### 9.2 `init [PATH]`

空のディレクトリへ作品プロジェクトと Git repository を作ります。`PATH` 省略時は現在のディレクトリです。初期化済み、ファイルへのパス、存在しないパス、空でない未初期化ディレクトリは変更しません。

### 9.3 `status`

API を呼び出さず、ファイルを変更せずに次を表示します。

- 作品ルート
- 現在の phase
- 最後と実行中の要求
- 現在の章と次の話
- 完了章・話、未処理 review・decision の数
- ロック情報
- 次の標準処理

実ファイルとの軽い不一致は `Warning:` として表示されます。完全な検査には `validate` を使います。

### 9.4 `validate`

API を呼び出さず、次を可能な範囲でまとめて検査します。

- 設定 JSONC と参照関係
- state、run、成果物、要求、報告の対応
- ファイル番号、phase、記録済み hash
- 管理パス、シンボリックリンク、Git 状態
- `.gitignore` と API キー環境変数の存在

問題は `ERROR コード 説明` または `WARNING コード 説明` の1行形式です。`validate` は自動修復、Git add、API 接続を行いません。

### 9.5 `run`

未処理要求を1件処理します。事前に作品ルート、設定、状態、Git、ロック、要求、認証、接続を検査します。接続確認が成功するまでは作品ファイルを変更しません。

処理開始時に人間が編集した要求・設定・明示的な追加資料を `Record request NNNN input` として commit し、終了時に管理成果物を `Complete request NNNN: <status>` として commit します。未処理要求がなければ `No pending request.` と表示して正常終了します。

### 9.6 `check-llm`

```console
story-pipeline check-llm
```

設定の role から参照される全モデルについて、通常の Chat Completion と strict JSON Schema による構造化 JSON 応答を実際に生成できるか検査します。`PASS` が両方表示されたモデルは、Story Pipeline が最低限必要とする応答機能を利用できます。`FAIL` の場合は表示された失敗分類を確認してください。

このコマンドは作品、状態、実行記録、Git、ロックを変更しません。ただし実際の API 呼び出しをモデルごとに2回以上行うため、利用量と料金が発生する場合があります。API キーや完全な応答は表示しません。

### 9.7 `migrate-state`

旧版で、章内最終話の完成後も誤った制作フェーズを指す状態を、章・話対応表と既存本文から再計算します。作品本文、要求、run、既存 commit は変更しません。通常は使わず、更新案内または検証結果が必要性を示した場合だけ実行してください。

実行前に active request がなく、ロックがなく、Git が通常状態で、章・話番号と完成済み本文が連続している必要があります。状態が既に正しければ何も変更しません。変更時は `Migrate story state` commit が作られます。

### 9.8 `recover --abandon-active`

状態ファイルや run の不整合により通常の `run`、`validate`、`migrate-state` では作業を再開できない場合に使用します。`--abandon-active` は、進行中要求、未処理レビュー、未回答判断を再開対象から外すことへの明示的な同意です。

コマンドは最初に、ignored と `.env`、`run.lock` を除く未コミット差分を列挙し、`Preserve worktree before recovery` commit に保存します。保存できなければ状態を変更しません。その後、既存の構想・設定・構成・章対応表・本文から進行状態を再構築し、`.story-pipeline/state.json` だけを `Recover story state` commit に保存します。作品、要求、既存 run は削除しません。

実行ロック、Git競合、連続していない章・話番号、章対応表にない本文がある場合は、安全に判断できないため停止します。復旧後は新しい要求ファイルへ内容を書き、通常どおり `story-pipeline run` を実行します。

### 9.9 終了コード

| コード | 意味 | 主な対応 |
| ---: | --- | --- |
| 0 | 正常終了。警告だけの `status` / `validate` を含む | 出力を確認して続行 |
| 2 | コマンドの使い方が不正 | `--help` を確認 |
| 3 | 未初期化、作品ルートを特定できない | 作品配下へ移動、または `init` |
| 4 | 設定、状態、作品ファイルの検証エラー | `Location` と `validate` を確認 |
| 5 | Git または作業ツリーのエラー | `git status` を安全に整理 |
| 6 | 実行ロックの競合 | 実行中プロセスとロックを確認 |
| 7 | API、モデル、応答形式の失敗 | 認証、接続、モデル、報告を確認 |
| 8 | 人間の判断・確認が必要 | 報告の判断 ID に回答 |
| 9 | ファイル I/O または内部エラー | 権限・容量を確認し、再現情報を報告 |

シェルでは直前の終了コードを、macOS/Linux なら `echo $?`、PowerShell なら `$LASTEXITCODE` で確認できます。

## 10. Git とファイルの安全な扱い

### 10.1 `run` 前に許される編集

基本的に人間が編集するのは次のものです。

- 処理対象の `requests/NNNN.md`
- `story-pipeline-config.jsonc`
- 要求で明示した追加資料

開始前から staged 変更が1件でもあると `run` は停止します。`git status` を確認し、自分の変更を適切に commit するか、意図的に stage を外してから実行してください。マージ、rebase、cherry-pick などの途中、detached HEAD、親 repository の一部、submodule でも実行できません。

### 10.2 管理ファイルを直接直した場合

追跡済みの作品・状態・報告などを直接変更すると、`run` は API 接続確認後に HEAD の内容へ復元する場合があります。復元対象は事前に表示されます。未追跡の管理ファイルは、誰が作ったか証明できないため自動削除せず停止します。

直接編集を残したい場合は、そのまま実行せず、まず差分を別の安全な場所へ控え、次要求として変更意図を書いてください。Story Pipeline に管理させないメモは、管理パスと重ならないファイル名を使います。

### 10.3 自動 commit の境界

1回の要求では通常、次の2種類の commit が作られます。

```text
Record request 0003 input
Complete request 0003: completed
```

後者の status は `completed`、`failed`、`awaiting-human` のいずれかです。次要求テンプレートは終了 commit の後に作られ、未追跡のまま残ります。Story Pipeline は push しないため、必要に応じて利用者がリモートへバックアップします。

### 10.4 同時実行しない

同じ作品に対する `run` は同時に1つだけです。実行中に別ターミナルから `run` するとロック競合で停止します。プロセスを強制終了するとロックが残る場合があるため、「トラブル対応」の手順に従ってください。

## 11. 実行記録、費用、進行状況の確認

### 11.1 処理報告

`requests/NNNN_agent.md` は最初に読むべき記録です。受理した要求、解釈、工程、変更ファイル、評価と改稿、物語上の変更、未解決問題、判断事項、次の標準処理が記載されます。失敗時はエラー分類、失敗工程、再開可能性を確認してください。

### 11.2 詳細な run JSON

`.story-pipeline/runs/NNNN.json` には、論理的な LLM 呼び出し、実際の通信試行、再試行待機、role とモデル、provider が返した usage、lifecycle、incident ID が記録されます。provider が usage や cost を返さない場合、Story Pipeline は推測せず `null` または `unknown` として扱います。

費用管理が重要な場合は、provider 側の利用上限・請求画面も併用してください。Story Pipeline の呼び出し上限は制作工程の暴走防止であり、通貨建ての予算上限ではありません。

### 11.3 長時間表示が変わらない場合

`run` は処理中、30秒ごとに heartbeat を標準エラーへ出します。heartbeat が続いていれば、応答待ちなどの工程が動作中です。ターミナルを閉じたり二重実行したりせず、設定した `timeout_seconds` と再試行回数を考慮して待ちます。

## 12. トラブル対応

### 12.1 エラーの読み方

一般的なエラーは次の3行です。

```text
Error: 利用者が理解できる原因
Location: 設定キーまたは作品ルート相対パス
Action: 安全な次の操作
```

まず `Action` を実行し、その後 `story-pipeline validate` で全体を検査します。予期しない障害では traceback の代わりに incident ID と component が表示されることがあります。同じ ID を run JSON と照合し、バージョン、実行コマンド、秘密を除いた出力とともに問題報告へ添えてください。

### 12.2 作品ルートが見つからない

`init` 以外のコマンドは、現在のディレクトリから親へ `story-pipeline-config.jsonc` を探します。作品ディレクトリまたはその配下へ移動してください。別作品の設定を誤って選ばないよう、途中で壊れた設定ファイルを見つけた場合はそこで停止します。

### 12.3 API キーまたは接続のエラー

1. `story-pipeline-config.jsonc` の `api_key_env` を確認する。
2. 同名の環境変数または dotenv の値が空でないことを確認する。
3. `base_url` とモデル識別子を provider の案内と照合する。
4. ネットワーク、利用枠、課金状態、モデルへのアクセス権を確認する。
5. `story-pipeline check-llm` を実行して通常応答と構造化応答を確認する。
6. `story-pipeline validate` 後に `run` を再実行する。

秘密値を確認するために画面へ API キーを出力したり、要求へ貼り付けたりしないでください。

### 12.4 Git エラー

```console
git status
git log -1 --oneline
```

staged 変更、競合、進行中の履歴操作、detached HEAD がないか確認します。自分の変更は内容を理解したうえで commit してください。問題解消のために `git reset --hard` や `git clean` を安易に使うと、要求や成果物を失う可能性があります。

Git hook や commit 署名が commit を拒否した場合、Story Pipeline はそれらを迂回しません。利用者の Git 設定側で解決します。

### 12.5 ロックが残った

`.story-pipeline/run.lock` がある場合、まず別ターミナルや別ホストで `run` が動いていないか確認します。`story-pipeline status` はロック情報を表示し、`validate` は stale の可能性を検査します。

同じ hostname の PID が存在せず、対応する run 記録がある場合に限り stale と判断できます。それでも自動削除はされません。プロセスが本当に存在しないことを利用者が確認してから、画面の案内に従ってロックファイルだけを削除し、`validate` を再実行してください。別 hostname、PID 確認権限なし、壊れたロックでは、状況を確認できる管理者へ相談してください。

### 12.6 `awaiting_human` になった

エラーではなく、安全な判断待ちです。処理報告から判断 ID、選択肢、影響を読み、次要求で明示的に回答します。設定した変更行数の判定値以上の変更、根本設定の遡及変更、矛盾、追加資料の秘密疑いなどでも発生します。

### 12.7 `failed` になった

失敗でも報告、状態、再開情報は可能な限り終了 commit に保存されます。空の次要求はそのままにし、処理報告の「未解決の問題」と「再開可能性」を確認します。原因を解消して同じ `run` を再実行してください。

本文評価後の知識更新だけが失敗した場合、検証済み本文は checkpoint に保存され、次回は本文を生成し直さず知識工程から再開できます。checkpoint や関連作品ファイルを手動変更すると再利用できなくなるため触らないでください。

### 12.8 `validate` が hash や対応関係のエラーを出す

管理ファイルの手編集、途中のファイル削除、手動 commit の範囲違いなどが考えられます。エラーコード、対象パス、直近の Git commit を確認し、履歴からどの変更で不一致になったか調べます。内容が不明なまま state や run JSON を書き換えないでください。旧版固有の phase 不整合だけは、条件を満たす場合に `migrate-state` で修正できます。

### 12.9 要求が空だと言われる

Markdown 見出し、空白、HTML コメントだけでは要求内容になりません。テンプレートの見出しの下へ、少なくとも実行してほしい内容を通常の Markdown で書いて保存してください。

## 13. バックアップ、移動、再開

### 13.1 バックアップ

作品ルート全体を Git repository としてリモートへ push すると、要求、作品、状態、実行記録をまとめて保全できます。ただし `.env` と実行ロックは push されません。別環境では API キーを安全に再設定します。

次要求テンプレートは未追跡なので、書きかけを含めてバックアップしたい場合は、内容を確認して利用者自身の commit に保存するか、別途安全に保全してください。ただし、その commit がある状態で次の `run` が期待どおり要求を検出するか、事前に `validate` で確認してください。

### 13.2 別の場所へ移動する

repository 全体を clone またはコピーし、作品ルートで次を実行します。

```console
story-pipeline --version
story-pipeline validate
story-pipeline status
```

設定の dotenv パス、API キー、Git identity を新しい環境に合わせます。`.story-pipeline/run.lock` は実行中プロセスに結び付くため、実行中の作品をコピーして別環境で同時に再開しないでください。

### 13.3 中断する

通常の長い API 待機を中断する場合、ターミナルから1回割り込み、終了処理とロック解放を待ってください。強制終了や電源断の後は、すぐ再実行せず `status`、`validate`、Git 状態、ロック、最後の処理報告と run JSON を確認します。

## 14. 用語集

| 用語 | 意味 |
| --- | --- |
| 作品ルート | `story-pipeline-config.jsonc` がある作品の最上位ディレクトリ |
| 要求 | 人間が書く `requests/NNNN.md` |
| 処理報告 | CLI が書く `requests/NNNN_agent.md` |
| 実行 | 1件の要求を受理し、報告と状態を保存するまで |
| 工程 | 実行内で再開できる処理単位 |
| 管理ファイル | CLI が生成・更新し、整合性を管理する作品・状態・報告ファイル |
| 人間入力 | 要求、設定、明示的に許可した追加資料 |
| phase | 構想、設定、執筆、改稿など現在の制作段階 |
| role | planner、writer などモデルに割り当てる制作上の役割 |
| 論理呼び出し | 生成や評価など、目的が1つの LLM 呼び出し |
| transport 試行 | 一時障害で同じ論理呼び出しを再送した各通信 |
| checkpoint | 検証済み本文を後続工程から再開するための内部保存 |
| pending decision | 人間の明示的な判断を待っている項目 |
| incident ID | 予期しない障害と run 記録を照合する識別子 |
