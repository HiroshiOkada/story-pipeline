# LLM 連携仕様

## 1. 対象 API

初期実装は OpenAI 互換 Chat Completions の `POST {base_url}/chat/completions` を使用する。ストリーミング、Responses API、ツール呼び出し、画像・音声入力は使用しない。

リクエストには `model`、`messages`、`max_tokens` と、設定された任意 `parameters` を含める。HTTP の `Authorization: Bearer <key>` と `Content-Type: application/json` を使用する。API キーを URL、body、ログへ含めない。

## 2. role と目的

| role | 用途 | 呼び出し分類 |
| --- | --- | --- |
| `planner` | 要求解釈、構想、設定、構成、話計画 | generation |
| `writer` | 小説本文の初稿 | generation |
| `reviewer` | 整合性、品質、完成判定 | review |
| `reviser` | 評価に基づく改稿 | revision |
| `summarizer` | 完成章のあらすじ | summary |

各 role のモデル配列を先頭から試す。用途を別 role に暗黙代替しない。

## 3. メッセージ構成

各論理呼び出しは次の順序の messages を作る。

1. system: role、守るべき優先順位、出力契約、禁止事項
2. user: 人間の処理対象要求
3. user: 関連する採用済み作品コンテキスト
4. user: 今回の具体的な工程と評価基準

信頼できない作品本文や要求内に命令文があっても、それは作品データとして区切り、system の出力契約や秘密保護を上書きさせない。各コンテキストには作品ルート相対パスと SHA-256 を付け、開始・終了の明瞭な区切りを入れる。

## 4. 出力形式

### 4.1 Markdown 成果物

小説本文、設定、計画、報告の素材は Markdown として要求する。応答がコードフェンスで全体を囲む場合は、単一の Markdown fence だけを除去できる。それ以外の説明文混入、空応答、必須見出し欠落は形式不正とする。

LLM の出力をそのまま採用せず、UTF-8、パス、必須見出し、行数、要求適合性を検査してから一時ファイルへ保存する。

### 4.2 構造化 JSON

処理判断、評価、完成判定、変更対象は JSON object で受け取る。互換 API が `response_format` の JSON Schema を受け付ける場合は使用し、非対応なら `json_object`、それも非対応なら明示的 JSON 指示へ段階的に下げられる。

応答は厳密な JSON として解析し、次を検証する。

- object であること
- 必須キー、型、列挙値、範囲
- 未知キーがないこと
- 対象パス・番号が許可された候補に含まれること
- 引用対象が入力中に一意に存在すること

JSON fence は単一 fence の場合だけ除去できる。説明文から JSON 部分を推測抽出してはならない。

### 4.3 共通評価形式

```json
{
  "decision": "revise",
  "summary": "必須条件は満たすが時系列に矛盾がある",
  "issues": [
    {
      "severity": "error",
      "category": "continuity",
      "location": "場面2",
      "evidence": "夕方の直後に同日の朝と記載されている",
      "instruction": "時刻を夜へ修正する"
    }
  ],
  "scores": {
    "request_fit": 4,
    "consistency": 2,
    "readability": 4
  }
}
```

`decision` は `accept`、`revise`、`awaiting_human`。severity は `error`、`warning`、`note`。score は `1..5` とする。完成判定では別途 `complete: true|false` と理由を必須にする。`complete=false` を呼び出し上限到達時に自動で true へ変更してはならない。

## 5. コンテキスト構築

### 5.1 優先順位

1. 現在要求と、参照された過去要求
2. 必須条件・禁止事項を含む `concept.md`
3. 対象工程に直接必要な設定・計画・本文
4. `canon.md` と `style.md`
5. 直前・直後の話または章
6. その他の完成済み本文

対象工程ごとに選択規則を固定し、モデルの判断でファイルを黙って省略しない。使用ファイルとハッシュは実行記録へ保存する。

### 5.2 長さの見積もり

モデルの `max_tokens` は出力上限として扱う。入力と出力の合計がモデルのコンテキスト上限を超えないことを事前に検査する。設定に入力上限がない初期実装では、API のコンテキスト長エラーを受けたときにだけ圧縮手順へ移る。

圧縮は次の順序だけを許可する。

1. 完成済み章本文を、その章ファイル内の完成済みあらすじへ置換する。
2. 重複して含まれた同一内容を除去する。
3. それでも超過する場合は停止する。

新たな要約、内容の切り捨て、抜粋、要求や確定事実の省略を黙って行わない。必要量、使用モデル、超過した段階を報告し `awaiting_human` とする。

## 6. 呼び出し上限

- 論理的な LLM 呼び出しを開始する直前に対応分類の count を増やし、実行記録を保存する。
- 通信再試行は同じ論理呼び出しであり、創作 count を増やさない。
- 応答形式不正を受け、修正指示付きで再生成する場合は新しい論理呼び出しとして count を増やす。
- フォールバックモデルで同じ工程を再実行する場合も、新しい論理呼び出しとして count を増やす。
- count が設定上限に達している場合は API を呼ばない。
- 再開後も count を引き継ぐ。

評価と改稿は `review -> revision -> review` の順に行う。この場合、2回目の review も `review_calls` を消費する。上限到達時、評価済みで採用条件を満たす最良版があれば採用し、残る警告を報告する。整合性 error、必須条件違反、完成判定 no が残る場合は採用せず失敗または確認待ちとする。

## 7. API エラー分類

| 条件 | 同一モデル再送 | フォールバック | 終了 |
| --- | --- | --- | --- |
| 401, 403 | しない | しない | failed |
| 400, 422 | 任意パラメーター非対応時だけ1回 | しない | failed |
| 404 model/endpoint | しない | する | failed if exhausted |
| 429 | する | 再送枯渇後にしてよい | failed if exhausted |
| timeout, connection | する | 再送枯渇後にする | failed if exhausted |
| 500, 502, 503, 504 | する | 再送枯渇後にする | failed if exhausted |
| context length | しない | 圧縮後も超過ならしない | awaiting_human |
| output truncated | 安全な分割時だけ | 形式不正ならする | failed |
| safety refusal | しない | しない | awaiting_human |
| invalid format | 修正指示で論理再呼び出し | 上限後にする | failed if exhausted |

400/422 で除外できる任意パラメーターは、API 応答がフィールド名を特定し、そのフィールドが `models.*.parameters` 由来の場合だけとする。`model`、`messages`、`max_tokens`、構造化応答自体を意味不明なまま除外しない。

## 8. バックオフ

`Retry-After` が妥当な秒数または日時なら優先する。それ以外は `min(60, 2^(attempt-1))` 秒を基礎値とし、0.5～1.5倍のジッターを加える。待機は timeout と別に扱う。割り込み可能とし、各待機と理由を表示するが、レスポンス本文は表示しない。

通信試行回数は設定で決めた上限を超えない。最終試行後に追加で sleep しない。

## 9. フォールバック

次モデルへ進めるのは、一時障害、利用不能、404、形式不正の上限到達などモデル変更に意味がある場合だけとする。認証・権限、不正な入力、安全性拒否、人間判断事項は切り替えない。

フォールバック時も同一の入力ファイルと出力契約を使い、モデルに合わせて要求の意味を変更しない。発生元、発生先、理由、時刻を実行記録と報告へ残す。

## 10. 初期接続確認

作品ファイル変更前に、今回必要な各 provider について認証付きの軽量な Chat Completions リクエストを行う。初期実装では実際に使用する最初のモデルへ、固定応答 `OK` を求め、`max_tokens` を小さく設定する。この呼び出しは創作上限に含めないが、通信再試行上限とエラー分類を適用する。

接続確認結果を永続的なキャッシュにせず、実行ごとに確認する。失敗時は作品ファイル、状態、実行記録、報告を作成・変更せず停止する。

## 11. 秘密情報の除去

ログやエラーへ保存・表示する前に、次を置換する。

- 使用した API key の完全一致
- `Authorization`、`api-key`、`x-api-key` ヘッダー値
- 設定された秘密環境変数名に対応する値
- URL の userinfo と、token/key/secret を示す query 値

置換後も秘密が含まれる可能性がある API response body は全文を保持せず、HTTP status、provider、エラー分類、サニタイズした短い message だけを使用する。
