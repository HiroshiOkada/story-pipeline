# 制作パイプライン詳細仕様

## 1. 1要求の共通工程

要求処理は次の固定工程を持つ。該当しない工程は実行記録で `skipped` とする。

| 工程 ID | 入力 | 出力 |
| --- | --- | --- |
| `interpret_request` | 対象要求、過去要求、状態 | 構造化された要求解釈 |
| `determine_scope` | 要求解釈、作品状態 | 今回の処理単位と更新候補 |
| `build_context` | 対象工程、作品ファイル | 使用コンテキスト一覧 |
| `generate` | 要求、コンテキスト | 新規案または変更案 |
| `mechanical_check` | 生成案 | 機械検査結果 |
| `review` | 生成案、評価基準 | 構造化評価 |
| `revise` | 生成案、評価 | 改稿案 |
| `consistency_check` | 採用候補、関連資料 | 整合性評価 |
| `adopt` | 評価済み候補 | 採用するファイル変更 |
| `update_state` | 採用結果 | state と run 更新 |
| `write_report` | 全工程の要約 | `requests/NNNN_agent.md` |

生成を伴わない修正、判断回答、検証だけの要求では不要な工程を省略できるが、解釈、範囲決定、状態更新、報告は省略しない。

## 2. 要求解釈

### 2.1 出力契約

```json
{
  "kind": "continue",
  "summary": "現在のフェーズを次の自然な単位まで進める",
  "targets": [],
  "required_conditions": [],
  "prohibited_changes": [],
  "additional_material": [],
  "decision_answers": [],
  "ambiguities": [],
  "requested_units": 1,
  "requested_until": null
}
```

`kind` は `create`、`continue`、`modify`、`add`、`reconsider`、`answer`、`mixed` のいずれかとする。`create`、`continue`、`answer` の `targets` は空配列とし、planner が標準工程の対象を補ってもパーサーが空へ正規化する。実際の対象は状態と採用済み成果物から決定する。

`modify`、`add`、`reconsider` と変更対象を伴う `mixed` では、入力中に文字列として明示された安全な作品ルート相対パスだけを `targets` に保持する。対象が欠ける、推測が必要、または管理対象外の場合は人間判断で停止する。変更対象を伴わない `mixed` の `targets` は空配列とする。

### 2.2 曖昧さと矛盾

次は人間判断を必要とする。

- 引用が存在しない、または複数一致する修正
- 同じ優先順位の要求同士の矛盾
- 根本方針変更に該当する要求で、変更意思が明示されていないもの
- 対象範囲外の生成要求
- 管理対象外ファイルへの変更要求

一方、人物名、細部の場所、仮タイトルなど根本を左右しない不足は仮定できる。仮定は構造化し、成果物と報告の両方へ明記する。

## 3. 作業範囲決定

### 3.1 標準継続

「そのまま進めてください」は状態と実ファイルを照合した上で、次の最初の該当規則を選ぶ。

1. `concept.md` がない: 構想を完成させる。
2. 基礎設定のいずれかがない、または pending review: 基礎設定を完成・評価する。
3. `plot.md` または必要な章計画がない: 全体構成を完成させる。
4. 次話計画がない: 次の1話の計画を作る。
5. 次話本文がない: その1話を執筆、評価、改稿、整合確認する。
6. 対象話に未完了工程がある: その処理を完了する。
7. 章の全話が完成し章評価がない: 章評価と必要な改稿を行う。
8. 全話が完成し全体改稿がない: 全体評価と改稿を行う。
9. 最終改稿済み: 完成判定と状態報告を行う。

要求が「3話分」など明示単位を持つ場合も、各話について全工程を終えてから次話へ進む。呼び出し・行数上限に達した時点で停止し、処理済みと残りを報告する。

### 3.2 根本変更

ジャンル、主人公・主要人物、結末、規模、必須条件、重要設定、完成話の大規模遡及改稿の変更は、要求に対象と変更意思が明示されている場合だけ範囲へ含める。単純継続中に必要だと判断しても変更せず、代替案と影響範囲を報告して `awaiting_human` とする。

## 4. フェーズ契約

### 4.1 構想 `concept`

入力は初期要求と既存の明示条件。出力は `concept.md` の全必須セクションとする。作品の根本が決められないほど情報不足なら確認待ち、それ以外は仮定を明記して進める。

受入条件:

- 必須条件と禁止事項を損なっていない。
- ジャンル、読者、着想、テーマ、規模が相互に矛盾しない。
- 人間の指定と CLI の仮定を区別している。

### 4.2 基礎設定 `foundation`

`world.md`、`characters.md`、`style.md`、`canon.md` を一つの整合単位として作成する。`canon.md` は初期時点の確定事実だけを含め、将来案を確定事項にしない。

受入条件:

- 世界ルールと人物能力に矛盾がない。
- 人物の目的・関係・変化が構想に寄与する。
- 視点、時制、表記ルールが決まっている。
- 整合性 review に error がない。

### 4.3 全体構成 `plotting`

`plot.md` と、直近の制作に必要な `chapters/NNNN.md` を作成する。全章の存在が必要な作品では章の一覧と接続条件を plot に持たせるが、遠い章を過度に場面詳細化しない。

受入条件:

- 開始、主要転換点、クライマックス、結末が接続する。
- 人物変化と伏線の設置・回収先が追跡可能である。
- 各章に開始・終了状態と収録話の範囲がある。

### 4.4 話計画 `episode_planning`

`episode_plans/NNNN.md` を生成し、章計画の目的を具体的な場面へ分解する。直前話が完成していれば実際の終了状態を開始状態へ反映する。

受入条件:

- 開始状態から終了状態への因果がある。
- 開示情報、伏線、感情変化、次話への引きが特定される。
- 目標文字数が正の整数で、要求された作品規模と整合する。

### 4.5 本文 `drafting`

1. 話計画、設定、canon、style、直前話、必要なら次話計画を読む。
2. 初稿を作る。
3. 機械検査を行う。
4. reviewer が要求適合と品質を評価する。
5. error または修正価値の高い warning があれば上限内で改稿する。
6. 整合性を再評価する。
7. 最良版を入力 hash と評価 hash に束縛した内部 checkpoint へ保存する。
8. 本文で確定した事実と人物状態を抽出し、evidence を検証する。
9. 本文、canon、人物状態を一つの採用単位として保存し、全出力 hash の一致後に checkpoint を採用済みにする。

本文の受入条件は必須条件違反なし、整合性 error なし、対象話として開始・終了が成立することとする。一般的な文章上の好みだけを理由に人間の指定文体を変更しない。

本文 JSON、Markdown 機械検査、評価、knowledge 抽出は独立した工程とする。本文評価通過後に knowledge が失敗した場合、正式な `episodes/` へはまだ保存せず、`.story-pipeline/checkpoints/NNNN/draft.json` から knowledge 工程だけを再開する。要求 revision、全入力 hash、本文 hash、評価対象 hash のいずれかが変わった checkpoint は再利用しない。

evidence は空白と改行を除いて照合し、元本文上で一意な場合だけ元の完全一致文字列へ戻して保存する。本文外、言い換え、複数一致は拒否する。

### 4.6 章改稿 `chapter_revision`

章内全話と前後章の接続情報を評価し、テンポ、反復、出番、時系列、視点、伏線、人物変化、長さを確認する。改稿は問題箇所へ限定し、完成話の大規模な再構成は確認待ちにする。

完成判定 `complete=true` 後、章のあらすじを `chapters/NNNN.md` に保存し、completed chapters を更新する。`false` のまま上限へ達した場合は未完成理由を報告する。

### 4.7 全体改稿と完成 `final_revision`, `completed`

章評価を統合し、全体の因果、人物変化、伏線、結末、要求適合を評価する。本文を一度に収められない場合は章あらすじと隣接章接続評価を使う。

小説全体への明示的な完成判定が `complete=true` の場合だけ `completed` へ遷移する。軽微な注意事項は報告へ残す。`false` または未評価なら完成扱いにしない。

## 5. 機械検査

LLM 評価前に、対象に応じて次を決定的に検査する。

- UTF-8、空ファイル、必須見出し
- Markdown fence やテンプレートコメントの残存
- 指定文字数に対する実文字数と許容範囲
- 登場人物名、固有用語、表記ルールの既知の不一致
- 話番号、章の収録範囲、前後接続
- 修正要求の引用が一意で、指定範囲外が不変であること
- API 応答由来の説明文や JSON の混入

文字数許容範囲は要求または style に明記があればそれを優先し、なければ目標の ±20% を warning とする。機械検査で安全に直せるのは末尾改行や単一外側 fence の除去に限る。物語内容を自動修正しない。

## 6. 評価と候補採用

### 6.1 評価優先順位

1. 人間の必須条件・禁止事項
2. 人物、設定、時系列、場所、所持品、視点、伏線の整合性
3. 人間が指定した品質観点
4. Web 小説向けの既定評価観点

1または2に error がある候補は採用不可。3と4の warning は呼び出し上限、改稿リスク、他スコアを考慮して採用できる。

### 6.2 最良版

各候補に入力ハッシュ、生成順、評価を対応付ける。採用可能候補を次で比較する。

1. 必須条件と整合性 error がない。
2. `request_fit` が高い。
3. `consistency` が高い。
4. 人間指定の個別スコアが高い。
5. 同点なら改稿回数が少なく、先に生成された候補。

未評価候補を「最良」として採用しない。採用理由と不採用候補の主要問題を報告する。

## 7. canon 更新

canon へ追加できるのは採用本文で読者に提示された事実、または採用済み設定で確定された事実だけとする。計画上の予定、却下案、LLM の推測を追加しない。

事実には可能な限り出典（設定ファイルまたは話番号）、成立時点、関係人物を記す。既存事実の変更は履歴を消さず、「失効・訂正」と理由を記載する。重要設定の遡及変更は明示要求なしに行わない。

## 8. 修正要求

- ファイル、引用、変更意図、範囲を検証する。
- 引用は改行正規化後の完全一致で検索し、1件だけでなければ変更しない。
- 変更案に対して指定範囲外の diff がないことを機械検査する。
- 指定範囲外の関連ファイル更新が必要な場合は、その理由と対象を要求から明確に導けるときだけ含める。
- 完成済み内容へ波及する大規模変更は影響一覧を示して確認待ちにする。

## 9. 報告生成

報告は実行記録と採用 diff を決定的な情報源とし、LLM に事実を自由生成させない。自然言語要約に LLM を使う場合も、ファイル一覧、呼び出し数、モデル、status、エラー、判断 ID はプログラムが挿入する。

各必須見出しには次を含める。

| 見出し | 必須内容 |
| --- | --- |
| 受け付けた要求 | 要求番号と短い要約 |
| 要求の解釈 | kind、対象、仮定、適用した優先順位 |
| 実行した処理 | 完了・失敗・省略した工程 |
| 作成・変更したファイル | 相対パスと変更種別 |
| 評価と改稿 | 呼び出し数、採用理由、残る注意 |
| 物語・設定上の変更 | canon、人物状態、伏線の変更 |
| 未解決の問題 | error、再開位置、未処理範囲 |
| 人間に判断してほしい事項 | 判断 ID、質問、影響、選択肢 |
| 次回の標準処理 | 現在状態から決定した1単位 |

秘密値、プロンプト、応答全文、却下本文の全文を含めない。該当なしの節は「なし」とする。
