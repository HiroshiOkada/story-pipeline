# Story Pipeline 仕様書

## 1. 文書の位置づけ

本書は、日本語の Web 小説を AI と人間が協調して制作する CLI「Story Pipeline」の現時点における仕様を整理したものである。

本プロジェクトはまだ構想・設計段階にあり、本書には確定した方針に加えて、実装前に決定が必要な事項も記載する。

## 2. 目的

Story Pipeline は、人間が Markdown で要求を提示し、CLI がその要求に基づいて小説の設計、執筆、評価、改稿、整合性管理を行うためのツールである。

完全自動で作品を完成させることよりも、次の反復によって人間の意図を継続的に反映できることを重視する。

1. 人間が要求を記述する。
2. CLI が要求を解釈し、有限回の生成・評価・改稿ループを実行する。
3. CLI が処理結果を報告する。
4. 人間が生成物と報告を確認し、次の要求を記述する。

## 3. 対象範囲

### 3.1 対象

- 主な対象は日本語の Web 小説とする。
- Web 小説以外の一般的な小説にも利用できる構成とする。
- 作品および関連資料はテキストとして管理する。
- 人間が読みやすいよう、作品および関連資料には Markdown を使用する。

### 3.2 対象外

初期の対象には、次の機能を含めない。

- 表紙および挿絵の生成
- 音声およびオーディオブックの生成
- PDF の生成および出版用組版
- ePub の生成
- ランディングページなどの Web サイト生成

## 4. 基本原則

### 4.1 人間と CLI の責務

人間が直接編集するのは要求ファイルだけとする。

人間は `requests/NNNN.md` に、新規作成、継続、修正、追加、再検討などの要求を記述する。既存の文章を修正したい場合は、対象箇所を要求ファイルへコピーし、修正内容や意図を添える。

CLI は次のファイルを作成・更新する。

- CLI の処理報告
- 作品コンセプト
- 世界設定
- 登場人物設定
- 全体構成
- 各話の計画
- 文体および表記ルール
- 作中の確定事実
- 各話本文
- 評価結果
- パイプラインの状態および履歴

人間はこれらの作品ファイルを直接編集しない。変更は新しい要求ファイルを介して指示する。

### 4.2 要求を正本とする

人間の明示的な要求は、CLI による推測や既存の計画より優先する。ただし、要求間に矛盾がある場合や、要求の解釈が作品の根本方針を大きく変える場合は、CLI が勝手に決定せず人間へ確認を求める。

### 4.3 有限の自律処理

CLI が行う生成・評価・改稿ループには回数または作業範囲の上限を設ける。単純な継続指示によって、作品全体を無制限に生成しない。

## 5. 要求と報告

### 5.1 ファイル命名規則

人間の要求と CLI の報告は `requests` ディレクトリに保存する。

```text
requests/
├── 0000.md
├── 0000_agent.md
├── 0001.md
├── 0001_agent.md
└── ...
```

- `NNNN.md`: 人間が記述する要求
- `NNNN_agent.md`: 同じ番号の要求に対する CLI の処理報告
- 番号は `0000` から始まる 4 桁の連番とする。
- 要求と報告は作業履歴として保持する。
- 過去の要求を書き換えて再処理するのではなく、新しい番号で追加要求を作成する。

### 5.2 未処理要求の判定

`NNNN.md` が存在し、対応する `NNNN_agent.md` が存在しない場合、その要求を未処理とみなす。

同じ要求の二重適用を避けるため、報告が存在する要求は通常実行では再処理しない。再実行または追加修正は、新しい要求ファイルによって指示する。

### 5.3 修正要求

修正要求には、対象ファイル名、対象箇所の引用、修正意図、変更範囲などを記述できる。

```markdown
# 第3話の会話修正

## 対象

`episodes/0003.md` の以下の会話。

> 「俺はもう戻らない」
>
> 彼は静かにそう告げた。

## 修正要求

主人公はまだ決意しきれていないため、断言を避けてください。
強がっているが迷いが伝わる会話にしてください。

それ以外の場面は変更しないでください。
```

引用された文章が存在しない場合、または同一の文章が複数存在して対象を一意に特定できない場合、CLI は危険な推測による変更を避ける。未処理理由と必要な確認を報告し、人間からの次の要求を待つ。

### 5.4 処理報告

`NNNN_agent.md` には原則として次の情報を記録する。

- 受け付けた要求
- 要求の解釈
- 実行した処理
- 作成または変更したファイル
- 評価と改稿の結果
- 物語および設定上の主な変更
- 解決できなかった問題
- 人間に判断してほしい事項
- 次回の標準処理

API キーなどの秘密情報は報告に含めない。

## 6. パイプライン

パイプラインは次のフェーズで構成する。

```text
構想
  ↓
基礎設定
  ↓
全体構成
  ↓
エピソード計画
  ↓
本文執筆
  ↓
全体改稿
  ↓
完成
```

### 6.1 構想

最初の要求から、作品の目的と制約を抽出する。

主な成果物は `concept.md` とし、次の内容を管理する。

- タイトルまたは仮タイトル
- ジャンル
- 想定読者
- 作品の中心的な着想
- 中心テーマ
- 作品規模
- Web 小説としての方針
- 人間が指定した必須条件と禁止事項
- CLI が仮定した事項

要求が不足していても、作品の根本を左右しない事項は CLI が仮決定できる。仮決定した内容は処理報告に明記する。

### 6.2 基礎設定

構想に基づいて、次の成果物を作成する。

- `world.md`: 世界、時代、場所、社会、制度、能力などの設定
- `characters.md`: 登場人物、関係、目的、変化、口調などの設定
- `style.md`: 文体、視点、表記、段落、会話などの規則
- `canon.md`: 作中で確定した事実

本文を執筆する前に、設定間の整合性を評価する。

### 6.3 全体構成

作品全体の流れを `plot.md` に記録する。

- 開始時の状況
- 主要な転換点
- クライマックス
- 結末
- 登場人物の変化
- 伏線と回収
- Web 連載上の部および話の構成

### 6.4 エピソード計画

各話の詳細な計画を `episode_plans/NNNN.md` に記録する。

各話の計画には原則として次の内容を含める。

- 話の目的
- 登場人物
- 開始時と終了時の状況
- 場面の一覧
- 明かす情報と伏せる情報
- 感情の変化
- 伏線の設置または回収
- 次話への引き
- 目標文字数

全話を最初から過度に詳細化せず、全体構成を維持しながら必要な範囲を順次詳細化する。

### 6.5 本文執筆

各話本文を `episodes/NNNN.md` に保存する。

1 話の標準的な処理は次のとおりとする。

1. 現在の要求、作品設定、全体構成、各話計画、前後関係を読み込む。
2. 初稿を生成する。
3. 機械的な検査を行う。
4. 評価モデルによる評価を行う。
5. 必要に応じて改稿する。
6. 設定、時系列、伏線、人物の状態との整合性を確認する。
7. 採用した本文と関連資料を保存する。
8. 処理結果を報告する。

### 6.6 全体改稿

一定数の話が完成するごとに、複数話を通した読書体験を評価する。

- 連載上のテンポ
- 同種の展開の反復
- 登場人物の出番の偏り
- 設定、時系列、視点の矛盾
- 伏線の不足や未回収
- 読者に提示済みの情報との整合性
- 登場人物の変化
- 各話の長さの偏り

全話完成後には、作品全体を対象とした最終評価と改稿を行う。

## 7. 「そのまま進めてください」の処理

### 7.1 意味

人間が要求ファイルに「そのまま進めてください」と記述した場合、次の意味として扱う。

> 前回までに採用された構想、設定、プロット、文体および人間の要求を維持し、現在のフェーズにおける次の自然な作業単位を実行する。

### 7.2 フェーズごとの処理

| 現在の状態 | 次の標準処理 |
| --- | --- |
| 構想が未作成 | 構想を作成する |
| 構想完成、基礎設定未作成 | 基礎設定を作成する |
| 基礎設定完成、全体構成未作成 | 全体構成を作成する |
| 次話の計画が未作成 | 次話に必要な計画を作成する |
| 次話が計画済み、本文未作成 | 次の 1 話を執筆、評価、改稿する |
| 本文の評価または改稿が未完了 | 対象話の処理を完了する |
| 一定数の話が完成 | 必要に応じて複数話の連続性を評価する |
| 全話完成 | 全体改稿を行う |
| 最終改稿済み | 完成状態を報告する |

本文執筆フェーズにおける標準作業量は「次の 1 話を完成させる」とする案を採用候補とする。複数話または特定フェーズまで進めたい場合、人間は作業範囲を明示できる。

```markdown
そのまま3話分進めてください。
```

```markdown
第1部が完成するまで進めてください。
```

### 7.3 継続時に許可される更新

単純な継続指示でも、CLI は通常の執筆に伴う次の更新を行える。

- 本文で確定した事実を `canon.md` に追加する。
- 登場人物の状態、位置、所持品などを更新する。
- 伏線の設置および回収状態を更新する。
- 次話の計画を詳細化する。
- 明白な矛盾や表記揺れを修正する。
- パイプラインの状態を更新する。

### 7.4 人間の確認を必要とする変更

次の変更は単純な継続指示だけでは行わず、人間に確認を求める。

- ジャンルの変更
- 主人公または主要人物の変更
- 結末の根本的な変更
- 作品規模の大幅な変更
- 人間が指定した必須条件の破棄
- 採用済みの重要設定の変更
- 完成済みエピソードに対する大規模な遡及改稿

確認事項は `_agent.md` に記録し、状態を人間の回答待ちとして終了する。人間は次の要求ファイルで回答する。

## 8. 日本語 Web 小説の評価

初期の評価観点として、次を使用する。

- 第 1 話および各話冒頭の引き
- 各話末尾の引きと次話への期待
- 段落、改行、文の長さによる読みやすさ
- 会話と地の文のバランス
- 登場人物ごとの口調の区別
- 説明過多および設定の一括提示
- 視点の一貫性
- 同じ表現、比喩、語尾、構文の反復
- 連載全体のテンポ
- 人物、設定、時系列、所持品などの整合性
- その話によって物語や人物関係が進展したか
- タイトル、あらすじ、各話タイトルの訴求力

日本語向けの機械的検査と LLM による評価を組み合わせる。執筆モデルと評価モデルは別々に設定できるものとする。

評価および改稿のループには上限を設ける。上限到達時は最良の版を採用するか、未解決の問題を報告して人間の判断を待つ。

## 10. CLI

### 10.1 インストール

Python パッケージとして提供し、`uv tool install` でインストール可能にする。

```bash
uv tool install story-pipeline
```

パッケージの `pyproject.toml` にコマンドのエントリーポイントを定義する。

```toml
[project.scripts]
story-pipeline = "story_pipeline.cli:main"
```

パッケージ名およびコマンド名の最終決定は未了であり、上記は仮称である。

### 10.2 空ディレクトリでの実行

空ディレクトリで引数なしの CLI を実行した場合、作品用 scaffold を生成して終了する。

```bash
mkdir my-novel
cd my-novel
story-pipeline
```

空でない未初期化ディレクトリでは、既存ファイルを変更せず、明示的な初期化方法を案内する。

初期化済みのディレクトリでは、最寄りの `story-pipeline.toml` を作品ルートとして扱う案を採用候補とする。

### 10.3 サブコマンド案

```text
story-pipeline init       scaffold を生成する
story-pipeline run        次の未処理要求を処理する
story-pipeline status     現在のフェーズと進捗を表示する
story-pipeline validate   設定、作品ファイル、状態の整合性を検査する
```

引数なしの実行は、ディレクトリの状態に応じた省略形とする案を採用候補とする。

| 状態 | 動作 |
| --- | --- |
| 空ディレクトリ | `init` 相当 |
| 初期化済み | `run` 相当 |
| 空でない未初期化 | 説明を表示し、変更せず終了 |

## 11. AI プロバイダー

### 11.1 API 互換性

モデル接続には OpenAI 互換 API を使用する。OpenAI だけでなく、互換 API を提供する他社サービスおよびローカル推論サーバーを利用できるようにする。

接続先とモデルは作品の設定ファイルで切り替えられるものとし、作品生成のロジックを特定プロバイダーへ依存させない。

### 11.2 接続設定

設定ファイルには次の情報を記載する。

- OpenAI 互換 API のベース URL
- API キーを格納した環境変数名
- 使用するモデル名
- 執筆、評価、要約など用途別のモデル
- タイムアウト
- リトライ回数
- 温度など、互換性を確認できる生成パラメーター
- 読み込む `.env` ファイルのパス

設定ファイルの形式は TOML を有力候補とする。

```toml
[dotenv]
files = ["~/.env", ".env"]

[providers.openai]
base_url = "https://api.openai.com/v1"
api_key_env = "OPENAI_API_KEY"

[providers.local]
base_url = "http://localhost:1234/v1"
api_key_env = "LOCAL_LLM_API_KEY"

[models.writer]
provider = "openai"
model = "example-writer-model"
temperature = 0.8

[models.reviewer]
provider = "openai"
model = "example-reviewer-model"
temperature = 0.2
```

### 11.3 API キー

- API キーそのものを設定ファイルへ記載しない。
- 設定ファイルには API キーが格納された環境変数名を記載する。
- `python-dotenv` を利用し、`.env` から環境変数を読み込めるようにする。
- `.env` は作品ディレクトリ内に限定せず、HOME ディレクトリなど任意の場所を指定可能にする。
- `~` を HOME ディレクトリへ展開する。
- 起動時点で設定済みの環境変数を `.env` で上書きしない。
- API キーをログ、報告、状態ファイル、通常のエラー表示へ出力しない。
- 作品ディレクトリ内の `.env` は Git 管理対象外とする。

## 12. 状態管理と途中再開

CLI は、現在のフェーズ、次に処理する話、完了した話、保留事項、最後に処理した要求などを機械可読な状態ファイルで管理する。

```json
{
  "phase": "drafting",
  "next_episode": 4,
  "completed_episodes": [1, 2, 3],
  "current_arc": 1,
  "pending_reviews": [],
  "pending_decisions": [],
  "last_request": 4
}
```

要求の処理状態として、少なくとも次を表現できるようにする。

```text
pending → running → completed
                  ↘ failed
                  ↘ awaiting_human
```

API エラーやプロセス中断後に再実行した場合、完了済みの工程を不必要に繰り返さず、安全に処理を再開できる設計とする。

`state.json` だけを絶対的な正解とはせず、実際の要求、報告、作品ファイルと照合し、不一致を検出して報告する。

## 13. 安全性

- 空でない未初期化ディレクトリを暗黙に変更しない。
- API キーなどの秘密情報を成果物へ保存しない。
- 対象を一意に特定できない修正要求を推測で適用しない。
- 人間の明示した必須条件を単純な継続指示で破棄しない。
- 自動処理の作業量、API 呼び出し、評価および改稿回数に上限を設定する。
- CLI が Git を管理する場合でも、利用者の作業ツリーに対する破壊的な Git 操作を行わない。
- 初期接続確認に失敗した場合、作品ファイルを変更せず、必要な設定を案内する。

## 14. 参考プロジェクトから採用する考え方

設計の参考として NousResearch/autonovel を使用する。

主に次の考え方を参考にする。

- 世界、人物、構成、文体、本文、確定事実を別レイヤーとして管理する。
- 設定、執筆、評価、改稿を段階的なパイプラインとして扱う。
- 生成、評価、採用または再生成のループを設ける。
- 本文で確定した事実を後続話のコンテキストとして蓄積する。
- 執筆モデルと評価モデルを分けられるようにする。
- 進捗と評価結果を機械可読な形式で記録する。

次の要素は本プロジェクトの初期対象には含めない、またはそのまま採用しない。

- 画像、音声、出版用組版などの生成
- 英語に特化した文章評価ルール
- 特定の AI プロバイダーおよびモデルへの固定
- 自動的な `git reset --hard` による成果物の破棄

## 15. 未決定事項

実装計画を確定する前に、少なくとも次の事項を決定する。

1. パッケージ名と CLI コマンド名
2. 設定ファイル名と形式
3. 引数なし実行の最終的な挙動
4. 「そのまま進めてください」に対する標準作業量
5. 1 回の起動で処理する未処理要求の件数
6. 生成、評価、改稿の標準上限
7. 作品ファイルの変更履歴を管理する方法
8. API エラー時の再試行および再開方式
9. OpenAI Chat Completions API と Responses API の対応範囲
10. プロバイダー間で異なる機能およびパラメーターの扱い
11. 日本語 Web 小説の評価項目、重み、合格基準
12. 何話ごとに複数話の連続性評価を行うか
13. 人間の確認待ちを発生させる具体的な判定基準
14. scaffold に最初から作成するファイルの最終構成

## 16. 現時点の推奨標準値

未決定事項の検討を始めるための暫定案を次に示す。これらは確定仕様ではない。

- パッケージ名およびコマンド名: `story-pipeline`
- 設定ファイル: `story-pipeline.toml`
- 設定形式: TOML
- 引数なしで空ディレクトリから実行: scaffold を生成して終了
- 引数なしで初期化済みディレクトリから実行: 次の未処理要求を 1 件処理
- 単純な継続指示の標準作業量: 次の 1 話の計画、執筆、評価、改稿
- 1 回の起動で処理する要求: 最も若い未処理要求 1 件
- 1 話に対する評価および改稿: 最大 3 回
- 人間への質問: 対話入力ではなく `_agent.md` に記録して終了
- API: 初期実装では広く互換性のある方式を一つに限定し、追加方式は後から拡張
