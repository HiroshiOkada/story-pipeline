# Story Pipeline 仕様書

## 1. 文書の位置づけ

本書は、日本語の Web 小説を AI と人間が協調して制作する CLI「Story Pipeline」の現時点における仕様を整理したものである。

本プロジェクトはまだ構想・設計段階にあり、本書には確定した方針に加えて、実装前に決定が必要な事項も記載する。

## 2. 目的

Story Pipeline は、人間が Markdown で要求を提示し、CLI がその要求に基づいて小説の設計、執筆、評価、改稿、整合性管理を行うためのツールである。

完全自動で作品を完成させることよりも、次の反復によって人間の意図を継続的に反映できることを重視する。

1. 人間が要求を記述する。
2. CLI が要求を解釈し、有限回の生成・評価・改稿ループを実行する。
3. CLI が処理結果を報告する。
4. 人間が生成物と報告を確認し、次の要求を記述する。

## 3. 対象範囲

### 3.1 対象

- 主な対象は日本語の Web 小説とする。
- Web 小説以外の一般的な小説にも利用できる構成とする。
- 作品および関連資料はテキストとして管理する。
- 人間が読みやすいよう、作品および関連資料には Markdown を使用する。

### 3.2 対象外

初期の対象には、次の機能を含めない。

- 表紙および挿絵の生成
- 音声およびオーディオブックの生成
- PDF の生成および出版用組版
- ePub の生成
- ランディングページなどの Web サイト生成

## 4. 基本原則

### 4.1 人間と CLI の責務

人間が直接編集するのは要求ファイルだけとする。

人間は `requests/NNNN.md` に、新規作成、継続、修正、追加、再検討などの要求を記述する。既存の文章を修正したい場合は、対象箇所を要求ファイルへコピーし、修正内容や意図を添える。

CLI は次のファイルを作成・更新する。

- CLI の処理報告
- 作品コンセプト
- 世界設定
- 登場人物設定
- 全体構成
- 各話の計画
- 文体および表記ルール
- 作中の確定事実
- 各話本文
- 処理報告に含まれる評価結果
- パイプラインの状態および履歴

人間はこれらの作品ファイルを直接編集しない。変更は新しい要求ファイルを介して指示する。

### 4.2 要求を正本とする

人間の明示的な要求は、CLI による推測や既存の計画より優先する。ただし、要求間に矛盾がある場合や、要求の解釈が作品の根本方針を大きく変える場合は、CLI が勝手に決定せず人間へ確認を求める。

### 4.3 有限の自律処理

CLI が行う生成・評価・改稿ループは、LLM 呼び出し回数によって制限する。各処理に許可する呼び出し回数は設定ファイルで数回までに制限し、単純な継続指示によって作品全体を無制限に生成しない。

## 5. 要求と報告

### 5.1 ファイル命名規則

人間の要求と CLI の報告は `requests` ディレクトリに保存する。

```text
requests/
├── 0000.md
├── 0000_agent.md
├── 0001.md
├── 0001_agent.md
└── ...
```

- `NNNN.md`: 人間が記述する要求
- `NNNN_agent.md`: 同じ番号の要求に対する CLI の処理報告
- 番号は `0000` から始まる 4 桁の連番とする。
- 要求と報告は作業履歴として保持する。
- 過去の要求を書き換えて再処理するのではなく、新しい番号で追加要求を作成する。
- CLI は要求の処理と終了時コミットを完了した後、次の連番の要求ファイルを作成する。
- 次の要求ファイルは人間が編集するための未コミットファイルとして残し、次回の CLI 開始時にコミットする。

### 5.2 未処理要求の判定

`NNNN.md` が存在し、対応する `NNNN_agent.md` が存在しない場合、その要求を未処理とみなす。

同じ要求の二重適用を避けるため、報告が存在する要求は通常実行では再処理しない。再実行または追加修正は、新しい要求ファイルによって指示する。

1 回の CLI 起動では、最も若い未処理要求を 1 件だけ処理する。後続の要求は、先行する要求の処理報告を人間が確認できる状態になるまで処理しない。

### 5.3 修正要求

修正要求には、対象ファイル名、対象箇所の引用、修正意図、変更範囲などを記述できる。

```markdown
# 第3話の会話修正

## 対象

`episodes/0003.md` の以下の会話。

> 「俺はもう戻らない」
>
> 彼は静かにそう告げた。

## 修正要求

主人公はまだ決意しきれていないため、断言を避けてください。
強がっているが迷いが伝わる会話にしてください。

それ以外の場面は変更しないでください。
```

引用された文章が存在しない場合、または同一の文章が複数存在して対象を一意に特定できない場合、CLI は危険な推測による変更を避ける。未処理理由と必要な確認を報告し、人間からの次の要求を待つ。

### 5.4 処理報告

`NNNN_agent.md` には原則として次の情報を記録する。

- 受け付けた要求
- 要求の解釈
- 実行した処理
- 作成または変更したファイル
- 評価と改稿の結果
- 物語および設定上の主な変更
- 解決できなかった問題
- 人間に判断してほしい事項
- 次回の標準処理

API キーなどの秘密情報は報告に含めない。

## 6. パイプライン

パイプラインは次のフェーズで構成する。

```text
構想
  ↓
基礎設定
  ↓
全体構成
  ↓
エピソード計画
  ↓
本文執筆
  ↓
全体改稿
  ↓
完成
```

### 6.1 構想

最初の要求から、作品の目的と制約を抽出する。

主な成果物は `concept.md` とし、次の内容を管理する。

- タイトルまたは仮タイトル
- ジャンル
- 想定読者
- 作品の中心的な着想
- 中心テーマ
- 作品規模
- Web 小説としての方針
- 人間が指定した必須条件と禁止事項
- CLI が仮定した事項

要求が不足していても、作品の根本を左右しない事項は CLI が仮決定できる。仮決定した内容は処理報告に明記する。

### 6.2 基礎設定

構想に基づいて、次の成果物を作成する。

- `world.md`: 世界、時代、場所、社会、制度、能力などの設定
- `characters.md`: 登場人物、関係、目的、変化、口調などの設定
- `style.md`: 文体、視点、表記、段落、会話などの規則
- `canon.md`: 作中で確定した事実

本文を執筆する前に、設定間の整合性を評価する。

### 6.3 全体構成

作品全体の流れを `plot.md` に記録する。

- 開始時の状況
- 主要な転換点
- クライマックス
- 結末
- 登場人物の変化
- 伏線と回収
- Web 連載上の部および話の構成

作品には複数の話をまとめる「章」を設け、章ごとの計画を `chapters/NNNN.md` に保存する。各章について、目的、開始状態、終了状態、主要な出来事、含まれる話、前後の章との接続条件を管理する。

### 6.4 エピソード計画

各話の詳細な計画を `episode_plans/NNNN.md` に記録する。

各話の計画には原則として次の内容を含める。

- 話の目的
- 登場人物
- 開始時と終了時の状況
- 場面の一覧
- 明かす情報と伏せる情報
- 感情の変化
- 伏線の設置または回収
- 次話への引き
- 目標文字数

全話を最初から過度に詳細化せず、全体構成を維持しながら必要な範囲を順次詳細化する。

### 6.5 本文執筆

各話本文を `episodes/NNNN.md` に保存する。

1 話の標準的な処理は次のとおりとする。

1. 現在の要求、作品設定、全体構成、各話計画、前後関係を読み込む。
2. 初稿を生成する。
3. 機械的な検査を行う。
4. 評価モデルによる評価を行う。
5. 必要に応じて改稿する。
6. 設定、時系列、伏線、人物の状態との整合性を確認する。
7. 採用した本文と関連資料を保存する。
8. 処理結果を報告する。

### 6.6 全体改稿

各章の完成時に、その章の内部と前後の章を対象として連続性を評価する。

- 章内および章間のテンポ
- 同種の展開の反復
- 登場人物の出番の偏り
- 設定、時系列、視点の矛盾
- 伏線の不足や未回収
- 読者に提示済みの情報との整合性
- 登場人物の変化
- 各話の長さの偏り

全話完成後には、作品全体を対象とした最終評価と改稿を行う。作品全体を一度に扱えない場合も、章単位の評価結果と隣接する章の接続評価を統合する。

### 6.7 完成判定

章または小説の完成は、LLM に対象が小説または章として完成しているかを明示的に質問し、構造化応答で `yes` と判定された場合に成立する。

`no` の場合は、理由と不足事項に基づいて呼び出し回数上限内で修正と再評価を行う。上限まで `yes` にならなかった場合は完成扱いにせず、現在の状態、未完成と判断された理由、必要な次の作業を `NNNN_agent.md` で人間へ報告して終了する。

章または小説が `yes` と判定された場合も、判定理由と残っている軽微な注意事項を `NNNN_agent.md` で人間へ報告する。

## 7. 「そのまま進めてください」の処理

### 7.1 意味

人間が要求ファイルに「そのまま進めてください」と記述した場合、次の意味として扱う。

> 前回までに採用された構想、設定、プロット、文体および人間の要求を維持し、現在のフェーズにおける次の自然な作業単位を実行する。

### 7.2 フェーズごとの処理

| 現在の状態 | 次の標準処理 |
| --- | --- |
| 構想が未作成 | 構想を作成する |
| 構想完成、基礎設定未作成 | 基礎設定を作成する |
| 基礎設定完成、全体構成未作成 | 全体構成を作成する |
| 次話の計画が未作成 | 次話に必要な計画を作成する |
| 次話が計画済み、本文未作成 | 次の 1 話を執筆、評価、改稿する |
| 本文の評価または改稿が未完了 | 対象話の処理を完了する |
| 章内の全話が完成 | 章内と前後の章の連続性を評価する |
| 全話完成 | 全体改稿を行う |
| 最終改稿済み | 完成状態を報告する |

本文執筆フェーズにおける標準作業量は、次の 1 話について計画、執筆、評価、改稿、整合性確認まで完了することとする。構想・設定段階では、現在のフェーズを一つ完了する。複数話または特定フェーズまで進めたい場合、人間は作業範囲を明示できる。

```markdown
そのまま3話分進めてください。
```

```markdown
第1部が完成するまで進めてください。
```

### 7.3 継続時に許可される更新

単純な継続指示でも、CLI は通常の執筆に伴う次の更新を行える。

- 本文で確定した事実を `canon.md` に追加する。
- 登場人物の状態、位置、所持品などを更新する。
- 伏線の設置および回収状態を更新する。
- 次話の計画を詳細化する。
- 明白な矛盾や表記揺れを修正する。
- パイプラインの状態を更新する。

### 7.4 人間の確認を必要とする変更

次の変更は単純な継続指示だけでは行わず、人間に確認を求める。

- ジャンルの変更
- 主人公または主要人物の変更
- 結末の根本的な変更
- 作品規模の大幅な変更
- 人間が指定した必須条件の破棄
- 採用済みの重要設定の変更
- 完成済みエピソードに対する大規模な遡及改稿

確認事項は `_agent.md` に記録し、状態を人間の回答待ちとして終了する。人間は次の要求ファイルで回答する。

## 8. 日本語 Web 小説の評価

評価では整合性を厳格に判定し、それ以外の品質は人間の要求への適合度を基準とする。CLI 固有の好みや一般化された作法を、人間の要求より優先しない。

整合性評価では、少なくとも次を確認する。

- 人間の要求間の矛盾
- 人物、設定、時系列、場所、所持品の矛盾
- 視点と語り手の不整合
- 伏線の設置、維持、回収の不整合
- 章内の話の連続性
- 直前および直後の章との接続

人間の要求に含まれる場合は、次の観点も適合度評価に使用する。

- 第 1 話および各話冒頭の引き
- 各話末尾の引きと次話への期待
- 段落、改行、文の長さによる読みやすさ
- 会話と地の文のバランス
- 登場人物ごとの口調の区別
- 説明過多および設定の一括提示
- 視点の一貫性
- 同じ表現、比喩、語尾、構文の反復
- 連載全体のテンポ
- その話によって物語や人物関係が進展したか
- タイトル、あらすじ、各話タイトルの訴求力

日本語向けの機械的検査と LLM による評価を組み合わせる。執筆モデルと評価モデルは別々に設定できるものとする。

生成、評価および改稿の上限は、処理回数ではなく LLM 呼び出し回数で管理する。既定値は少数回とし、具体的な値は設定ファイルで指定する。上限到達時は最良の版を採用するか、未解決の問題を報告して人間の判断を待つ。

### 8.1 コンテキスト管理

章が完成した時点で、その章のあらすじを作成し、対応する `chapters/NNNN.md` に記録する。LLM に渡すコンテキストがモデルの上限へ近づいた場合、完成済みの章本文に代えて章のあらすじを使用する。

章のあらすじを使用してもコンテキスト上限を超える場合、CLI は内容をさらに圧縮したり一部を黙って省略したりせず、`NNNN_agent.md` に必要なコンテキスト量と停止理由を報告して処理を終了する。人間は次の要求を作成し、設定ファイルで 100M 級のトークンを扱えるモデルへ変更してから処理を再開する。

## 9. 作品ディレクトリ

想定する作品ディレクトリは次のとおりである。

```text
作品ディレクトリ/
├── story-pipeline-config.jsonc
├── requests/
│   ├── 0000.md
│   ├── 0000_agent.md
│   └── ...
├── chapters/
│   ├── 0001.md
│   └── ...
├── episode_plans/
│   ├── 0001.md
│   └── ...
├── episodes/
│   ├── 0001.md
│   └── ...
├── concept.md
├── world.md
├── characters.md
├── plot.md
├── style.md
├── canon.md
├── .story-pipeline/
│   ├── state.json
│   ├── runs/
│   │   ├── 0000.json
│   │   └── ...
│   └── run.lock
└── .gitignore
```

初期 scaffold では、CLI が生成すべき作品ファイルを空の状態で作成せず、最初の要求処理時に生成する。

scaffold は次の最小構成とする。

```text
作品ディレクトリ/
├── story-pipeline-config.jsonc
├── requests/
│   └── 0000.md
├── chapters/
├── episode_plans/
├── episodes/
├── .story-pipeline/
│   └── state.json
└── .gitignore
```

`concept.md`、`world.md`、`characters.md`、`plot.md`、`style.md`、`canon.md` は、最初の要求処理で必要になった時点に CLI が生成する。`.story-pipeline/runs/` は最初の要求処理時に作成し、`.story-pipeline/run.lock` は CLI の実行中だけ作成する。

## 10. CLI

### 10.1 インストール

Python パッケージとして提供し、`uv tool install` でインストール可能にする。

```bash
uv tool install story-pipeline
```

パッケージの `pyproject.toml` にコマンドのエントリーポイントを定義する。

```toml
[project.scripts]
story-pipeline = "story_pipeline.cli:main"
```

パッケージ名および CLI コマンド名は、いずれも `story-pipeline` とする。

### 10.2 引数なし実行と初期化

引数なしで CLI を実行した場合は、ディレクトリの状態にかかわらずヘルプを表示して終了する。scaffold の生成や要求の処理は行わない。

```bash
mkdir my-novel
cd my-novel
story-pipeline init
```

空でない未初期化ディレクトリでは、既存ファイルを変更せず、明示的な初期化方法を案内する。

初期化済みのディレクトリでは、最寄りの `story-pipeline-config.jsonc` を作品ルートとして扱う。

### 10.3 サブコマンド案

```text
story-pipeline init       scaffold を生成する
story-pipeline run        次の未処理要求を処理する
story-pipeline status     現在のフェーズと進捗を表示する
story-pipeline validate   設定、作品ファイル、状態の整合性を検査する
story-pipeline migrate-state  検証済み作品ファイルから既存状態を明示的に移行する
story-pipeline recover --abandon-active  未記録情報を保全し、成果物から待機状態を再構築する
```

引数なしの実行はヘルプ表示のみとし、操作には明示的なサブコマンドを必要とする。

## 11. AI プロバイダー

### 11.1 API 互換性

モデル接続には OpenAI 互換 API を使用する。OpenAI だけでなく、互換 API を提供する他社サービスおよびローカル推論サーバーを利用できるようにする。

接続先とモデルは作品の設定ファイルで切り替えられるものとし、作品生成のロジックを特定プロバイダーへ依存させない。

初期実装は、広く互換性のある Chat Completions API を対象とする。Responses API は初期実装の対象外とし、将来必要になった場合に追加する。

LLM に処理判断、評価、変更対象などの機械処理用情報を求める場合は、構造化 JSON を使用する。小説本文、設定、章計画、各話計画、人間向け報告などの成果物には Markdown を使用する。JSON 応答を解析または検証できない場合は、設定された上限内で再試行する。

### 11.2 接続設定

設定ファイルには次の情報を記載する。

- OpenAI 互換 API のベース URL
- API キーを格納した環境変数名
- 使用するモデル名
- 執筆、評価、要約など用途別のモデル
- モデルごとの最大トークン数
- 用途ごとのフォールバックモデル
- タイムアウト
- リトライ回数
- 処理ごとの LLM 呼び出し回数上限
- 読み込む `.env` ファイルのパス

設定ファイル名は `story-pipeline-config.jsonc`、形式はコメント付き JSON（JSONC）とする。

```jsonc
{
  // 先に存在する環境変数は .env の値で上書きしない。
  "dotenv": {
    "files": ["~/.env", ".env"]
  },
  "providers": {
    "openai": {
      "base_url": "https://api.openai.com/v1",
      "api_key_env": "OPENAI_API_KEY"
    },
    "local": {
      "base_url": "http://localhost:1234/v1",
      "api_key_env": "LOCAL_LLM_API_KEY"
    }
  },
  "models": {
    "writer-primary": {
      "provider": "openai",
      "model": "example-writer-model",
      "max_tokens": 8192
    },
    "writer-fallback": {
      "provider": "local",
      "model": "example-local-model",
      // 省略時は 128K（131072）を使用する。
    }
  },
  "roles": {
    "writer": ["writer-primary", "writer-fallback"],
    "reviewer": ["writer-primary"]
  },
  "limits": {
    "generation_calls": 3,
    "review_calls": 3,
    "revision_calls": 3,
    "retry_calls_per_request": 2
  },
  "request": {
    "timeout_seconds": 120,
    "retry_attempts": 3
  }
}
```

モデルごとの最大トークン数は任意設定とし、未設定の場合は 128K トークン（131072）を既定値として使用する。それ以外の任意パラメーターも共通の既定値を使用し、未設定なら既定値へフォールバックする。互換 API が任意パラメーターを受け付けない場合は、そのパラメーターを除外して再試行できるようにする。ただし、モデル名、接続先、認証情報など処理の意味や安全性に関わる値を暗黙に推測しない。明示された最大トークン数は既定値より優先し、モデルや接続先に応じて暗黙に変更しない。

用途に複数のモデルが設定されている場合は、記載順をフォールバック順とする。認証エラーや不正な要求を別モデルへ送って隠蔽せず、一時障害、利用不能、モデル不存在などフォールバックが有効な場合に限って次のモデルを使用する。フォールバックの発生は処理報告に記録する。

### 11.3 API キー

- API キーそのものを設定ファイルへ記載しない。
- 設定ファイルには API キーが格納された環境変数名を記載する。
- `python-dotenv` を利用し、`.env` から環境変数を読み込めるようにする。
- `.env` は作品ディレクトリ内に限定せず、HOME ディレクトリなど任意の場所を指定可能にする。
- `~` を HOME ディレクトリへ展開する。
- 起動時点で設定済みの環境変数を `.env` で上書きしない。
- API キーをログ、報告、状態ファイル、通常のエラー表示へ出力しない。
- 作品ディレクトリ内の `.env` は Git 管理対象外とする。

### 11.4 API エラー

API エラーは種類ごとに次のように処理する。

| エラー | 処理 |
| --- | --- |
| 認証・権限エラー（401、403） | 再試行せず停止し、必要な環境変数名と設定箇所を報告する。キーの値は表示しない |
| 不正な要求（400、422） | 原則として再試行しない。任意パラメーター非対応が原因の場合だけ、そのパラメーターを除外して 1 回再試行する |
| モデルまたはエンドポイント不存在（404） | 設定済みのフォールバックモデルがあれば切り替える。なければ停止する |
| レート制限（429） | `Retry-After` を優先し、指数バックオフとジッターを用いて設定回数まで再試行する |
| タイムアウト、接続切断、一時的なネットワーク障害 | 指数バックオフとジッターを用いて設定回数まで再試行する |
| サーバー障害（500、502、503、504） | 設定回数まで再試行し、回復しなければフォールバックモデルを試す |
| コンテキスト長超過 | 完成済みの章本文を章のあらすじへ置き換える。それでも超過する場合は報告して停止し、人間によるモデル変更を待つ |
| 出力上限超過 | 応答形式と要求範囲を保ったまま安全に分割できる場合だけ分割する。内容欠落の可能性がある場合は報告して停止する |
| コンテンツ拒否、安全性拒否 | 自動的な言い換えで人間の要求を変質させず、理由を報告して人間の確認を待つ |
| 応答形式不正、途中で切れた応答 | 同じモデルで設定回数まで再試行し、その後フォールバックモデルを試す |

生成、評価、改稿には、それぞれ既定で最大 3 回の LLM 呼び出しを許可する。通信障害などの API 再試行は創作処理の上限と分離し、1 回の API 要求につき既定で最大 2 回までとする。いずれかの上限を超えた場合、状態を `failed` または `awaiting_human` として終了し、次回実行で安全に再開できる情報を保存する。

## 12. 状態管理と途中再開

### 12.1 処理状態

CLI は、現在のフェーズ、次に処理する話、完了した話、保留事項、最後に処理した要求などを `.story-pipeline/state.json` で管理する。

```json
{
  "phase": "drafting",
  "next_episode": 4,
  "completed_episodes": [1, 2, 3],
  "current_arc": 1,
  "pending_reviews": [],
  "pending_decisions": [],
  "last_request": 4
}
```

要求の処理状態として、少なくとも次を表現できるようにする。

```text
pending → running → completed
                  ↘ failed
                  ↘ awaiting_human
```

API エラーやプロセス中断後に再実行した場合、完了済みの工程を不必要に繰り返さず、安全に処理を再開できる設計とする。

`.story-pipeline/state.json` だけを絶対的な正解とはせず、実際の要求、報告、作品ファイルと照合し、不一致を検出して報告する。

CLI 内部ファイルは `.story-pipeline` ディレクトリへ保存する。

```text
.story-pipeline/
├── state.json
├── runs/
│   └── NNNN.json
└── run.lock
```

- `state.json` は、現在のフェーズ、次の章と話、完了済み項目、最後の要求番号、確認待ち状態、内部データ形式のバージョンを記録する。
- `runs/NNNN.json` は、要求ごとの完了済み処理、LLM 呼び出し回数、使用モデル、フォールバック、対象ファイルのハッシュ、エラー、再開位置を記録する。
- `run.lock` は同じ作品に対する CLI の二重起動を防ぐため、実行中だけ作成する。
- `state.json` と `runs/NNNN.json` は Git 管理対象とする。
- `run.lock` は `.gitignore` に記載し、Git 管理対象外とする。
- LLM の応答全文、独立した評価ファイル、プロンプトの恒久ログ、キャッシュ、作品ファイルの複製バックアップは初期実装では保存しない。

### 12.2 Git による履歴管理

作品ディレクトリは Git リポジトリとして管理する。scaffold の生成時に Git リポジトリでなければ初期化する。

CLI の通常処理では、開始時と終了時にコミットを作成する。

1. CLI は開始時に作業ツリーを検査し、ファイルを「人間が編集できる入力」「要求で明示された追加資料」「CLI が管理する作品ファイル」「想定していないファイル」に分類する。
2. 人間が編集できる入力である処理対象の `requests/NNNN.md` と設定ファイルの変更を開始時コミットに保存する。
3. 人間が参考資料などのファイルを追加し、処理対象の `requests/NNNN.md` でそのファイルをコミットするよう明示した場合、指定されたファイルも開始時コミットに保存する。
4. CLI が管理する作品ファイルに直接変更がある場合、そのファイルを直前のコミット時点へ戻す。復元対象は仕様で列挙された管理ファイルに限定する。
5. 想定していない名前または場所のファイルには触れず、開始時コミットにも含めない。
6. CLI は必要な復元と開始時コミットの成功後にだけ、要求の処理を開始する。
7. 終了時コミットは、CLI が作成・変更した作品ファイル、状態、処理報告を保存する。
8. 処理が失敗または人間の確認待ちになった場合も、報告と再開に必要な状態を終了時コミットに保存する。
9. 終了時コミットの後、CLI は人間が次の要求を記述するための `requests/NNNN.md` を作成する。

コミットメッセージは CLI が一貫した英語形式で生成し、要求番号と処理状態を含める。開始時または終了時に記録すべき変更がない場合、空コミットは作成しない。

終了時コミット後に作成する次の要求ファイルは、そのコミットには含めない。人間が内容を記述した後、次回の CLI 開始時コミットで初めて履歴へ記録する。このため、正常終了直後の作業ツリーには次の要求ファイルが未コミットファイルとして残る。

CLI は `git reset --hard`、既存履歴の書き換え、想定外ファイルの未記録変更の破棄を行わない。仕様で列挙された CLI 管理ファイルへの直接変更だけは、開始時検査で直前のコミットへ戻す。コミットに失敗した場合は作品の生成や更新を続行せず、原因を表示して停止する。

CLI 管理ファイルの復元には、対象パスを明示した `git restore` または同等の Git 操作を使用する。リポジトリ全体を対象とする復元は行わない。復元したファイル名は実行結果として表示し、`NNNN_agent.md` にも記録する。

追加資料をコミットする指示では、要求に記載された相対パスをコミット対象とする。明示されていないファイルを同じディレクトリから自動的に追加しない。指定パスが作品ディレクトリ外を指す場合、存在しない場合、または秘密情報を含む可能性がある場合はコミットせず、`NNNN_agent.md` で人間に確認する。追加資料は CLI 管理ファイルとはみなさず、その後の起動時にも自動復元しない。

## 13. 安全性

- 空でない未初期化ディレクトリを暗黙に変更しない。
- API キーなどの秘密情報を成果物へ保存しない。
- 対象を一意に特定できない修正要求を推測で適用しない。
- 人間の明示した必須条件を単純な継続指示で破棄しない。
- 1 回の要求処理で 1,000 行以上の追加または変更を適用する場合は、必ず人間の確認を求める。
- 自動処理の作業量、API 呼び出し、評価および改稿回数に上限を設定する。
- 利用者の作業ツリーに対する破壊的な Git 操作を行わない。
- 初期接続確認に失敗した場合、作品ファイルを変更せず、必要な設定を案内する。

1,000 行の判定は、作品の管理対象ファイルに対して追加または内容変更される行の合計で行う。削除行はカウントしない。

1,000 行以上の追加または変更が必要だと判明した場合、CLI は変更を開始せず、変更の概要と規模を `_agent.md` に報告して終了する。人間が次の要求に「続けてください」と記述した場合、1 回の要求につき最大 1,000 行を処理する。残りがある場合は処理済み範囲と残りの範囲を報告し、次の「続けてください」を待つ。この継続要求自体を各 1,000 行分に対する人間の確認とみなす。大規模変更案を一括保留しないため、`pending/` ディレクトリは使用しない。

## 14. 参考プロジェクトから採用する考え方

設計の参考として NousResearch/autonovel を使用する。

主に次の考え方を参考にする。

- 世界、人物、構成、文体、本文、確定事実を別レイヤーとして管理する。
- 設定、執筆、評価、改稿を段階的なパイプラインとして扱う。
- 生成、評価、採用または再生成のループを設ける。
- 本文で確定した事実を後続話のコンテキストとして蓄積する。
- 執筆モデルと評価モデルを分けられるようにする。
- 進捗と評価結果を機械可読な形式で記録する。

次の要素は本プロジェクトの初期対象には含めない、またはそのまま採用しない。

- 画像、音声、出版用組版などの生成
- 英語に特化した文章評価ルール
- 特定の AI プロバイダーおよびモデルへの固定
- 自動的な `git reset --hard` による成果物の破棄
